# 1. 연구 배경 및 비즈니스 니즈

실전 1에서는 금융사 사내 문서에서 개인정보를 탐지하는 세 가지 방식(규칙 기반·토큰 분류 모델·LLM)을 비교하고, 미탐 최소화를 최우선 기준으로 **KoELECTRA-Ko-PII-NER**을 최종 탐지기로 선정하였다.

그러나 탐지만으로는 RAG 서비스를 운영할 수 없다. 탐지된 개인정보를 어떻게 처리하느냐에 따라 두 가지 문제가 발생한다.

- **단순 마스킹(\*\*\*):** 실명이 지워지므로 유출은 막을 수 있으나, "같은 사람이 어느 문서에 나오는가"라는 연결 정보까지 사라져 **이름 기반 검색이 불가능**해진다.
- **원문 그대로 적재:** 검색은 가능하나 벡터 DB·LLM 로그·외부 API로 개인정보가 그대로 흘러 **유출 위험**이 발생한다.

실전 2는 이 두 문제를 동시에 해결하는 **결정적 토큰 기반 가명처리**를 구현하는 단계이다.

> "실명이 하나도 없는 데이터로도 '윤선영 고객 대출 상담 내역 찾아줘'가 동작하게 만드는 것"

같은 사람은 문서가 달라도 항상 같은 가명 토큰이 되도록 처리하면, 이름을 몰라도 토큰으로 문서를 찾을 수 있다.

**실전 2의 위치.** 탐지(실전 1) → **가명처리·적재·검색(실전 2)** → 접근 통제·출력 재검사(종합)로 이어지는 파이프라인에서, 실전 2는 탐지 결과를 받아 실제로 동작하는 검색 챗봇을 처음으로 만드는 단계다. 가명처리의 정확도와 토큰 일관성이 이후 종합 단계의 품질을 결정한다.

# 2. AI 문제 정의

## 2.1 과제의 정형화

본 과제는 두 개의 하위 태스크로 구성된다.

**태스크 1. 결정적 가명처리 (Deterministic Pseudonymization)**

- **입력:** 원문 텍스트 + 탐지 결과 (label, start, end)
- **출력:** 가명처리된 텍스트 + 토큰-원문 매핑 테이블 (vault)
- **핵심 조건:** 같은 값 → 항상 같은 토큰, 다른 값 → 항상 다른 토큰

**태스크 2. 토큰 기반 검색 (Token-Filtered Semantic Search)**

- **입력:** 사용자 자연어 질의
- **출력:** 관련 문서 목록 + LLM 생성 답변 (가명 상태)
- **핵심 조건:** 질의에서 추출한 토큰으로 필터링 후 의미 검색 적용

## 2.2 두 가지 어려움

**어려움 1. 토큰 일관성 보장**

같은 사람이 문서마다 다른 표기로 등장한다. 정규화 없이 토큰화하면 동일인이 여러 토큰으로 쪼개져 검색이 깨진다.

| 원문 표기 | 정규화 후 | 기대 결과 |
|:---|:---|:---|
| 윤선영 | 윤선영 | 동일 토큰 ✅ |
| 윤 선영 | 윤선영 | 동일 토큰 ✅ |
| 010-1234-5678 | 01012345678 | 동일 토큰 ✅ |
| +82 10-1234-5678 | 01012345678 | 동일 토큰 ✅ |
| 770802-1978865 | 7708021978865 | 동일 토큰 ✅ |

**어려움 2. 동명이인 처리**

holdout 기준 동명이인은 4쌍(김민준·박도윤·이서연·정하은)이며, 이름이 같아도 서로 다른 인물이다. 실전 2에서는 이름 기반 단일 토큰을 적용하며, 동명이인은 의미 검색으로 보완한다. 완전한 구분은 종합 단계에서 처리한다.

| 동명이인 쌍 | 실전 2 처리 | 종합 단계 개선 |
|:---|:---|:---|
| 김민준 (HP057 직원 / HP058 고객) | 같은 토큰, 의미 검색으로 보완 | 역할 메타데이터 필터 |
| 박도윤 (HP061 / HP062 직원) | 같은 토큰, 의미 검색으로 보완 | 역할 메타데이터 필터 |
| 이서연 (HP059 / HP060) | 같은 토큰, 의미 검색으로 보완 | person_id 기반 토큰 |
| 정하은 (HP063 / HP064) | 같은 토큰, 의미 검색으로 보완 | person_id 기반 토큰 |

## 2.3 운영 제약

- **보안:** 임베딩·LLM API에는 가명처리된 텍스트만 전달. 원문·vault 전달 금지
- **키 관리:** HMAC_SECRET은 `.env`에만 보관. 코드 저장소 커밋 및 로그 출력 금지
- **일관성:** 같은 입력에 항상 같은 토큰 출력. 토큰이 흔들리면 검색이 깨짐
- **탐지기:** 가명처리는 실전 1에서 선정한 KoELECTRA의 결과만 사용

# 3. 연구 질문

- **RQ1.** 같은 사람이 문서마다 다른 표기로 등장해도 항상 동일한 토큰이 생성되는가? (토큰 일관성)
- **RQ2.** 가명처리된 텍스트만으로 임베딩·검색이 정상 동작하는가? (Hit@k, Recall@k 목표 달성)
- **RQ3.** 동명이인 질의에서 의미 검색이 올바른 인물의 문서를 상위에 올리는가?
- **RQ4.** 토큰 필터와 의미 검색을 결합했을 때 순수 의미 검색 대비 검색 정확도가 향상되는가?

# 4. 해결 접근

## 4.1 가명처리 파이프라인

```
문서 입력 (jsonl)
    ↓
[1] 탐지  — KoELECTRA-Ko-PII-NER
           개인정보 구간 (label, start, end) 추출
    ↓
[2] 정규화 — 표기 통일
           이름: 공백 제거
           번호류: 구분자(하이픈·점·공백) 제거
           국제전화: +82 → 0 변환
    ↓
[3] 토큰 생성 — HMAC-SHA256
           HMAC(정규화값 + ":" + label, key=HMAC_SECRET)
           앞 8자리 hex → <LABEL_XXXXXXXX>
    ↓
[4] vault 저장 — 토큰 ↔ 원문 매핑
           ON CONFLICT DO NOTHING (중복 방지)
    ↓
[5] 치환 — 원문 구간을 토큰으로 대체
           → chunk_text 생성
```

## 4.2 정규화 규칙 요약

| 대상 | 규칙 | 예시 |
|:---|:---|:---|
| 이름 | 공백 제거 | `윤 선영` → `윤선영` |
| 전화번호 | 구분자 제거, +82 → 0 변환 | `+82 10-1234-5678` → `01012345678` |
| 주민등록번호 | 구분자(공백·하이픈) 제거 | `770802 1978865` → `7708021978865` |
| 계좌번호 | 구분자 제거 (8가지 형식 대응) | `607-960055-16` → `60796005516` |
| 카드번호 | 구분자(공백·하이픈) 제거 | `9999 9999 9999 9999` → `9999999999999999` |
| 이메일 | 소문자 변환 | `SY.YOON07@Example.NET` → `sy.yoon07@example.net` |

> 정규화 규칙 전체 및 holdout 신규 형식 대응은 **가명처리 규칙 설계 산출물** 참조

## 4.3 벡터 DB 적재 파이프라인

```
[1] 가명처리 완료 chunk_text
    ↓
[2] 임베딩 API 호출
    chunk_text만 전달 (원문·vault 전달 금지)
    → vector(1536) 반환
    ↓
[3] chunks 테이블 INSERT
    doc_id, doc_type, split, chunk_text, tokens[], embedding
```

**테이블 구조 요약**

| 테이블 | 주요 필드 | 용도 |
|:---|:---|:---|
| chunks | doc_id, chunk_text, tokens[], embedding | 검색 대상 청크 저장 |
| vault | token, original, label, access_level | 토큰-원문 매핑, 접근 통제 |

## 4.4 검색 흐름

```
사용자 질의
    ↓
[1] 질의 가명처리 — 질의에서 개인정보 탐지 후 동일 토큰 생성
    ↓
[2] 토큰 필터 — WHERE tokens @> ARRAY['<PERSON_xxxx>']  (GIN 인덱스)
    ↓
[3] 의미 검색 — 코사인 유사도 기준 상위 k개 청크 선택
    ↓
[4] LLM 답변 생성 — 가명 텍스트만 전달
    ↓
[5] 출력 — 토큰 상태 그대로 반환 (실전 2 기본형)
```

**검색 패턴 분류 (holdout 질의 88개 기준)**

| 패턴 | 질의 수 | 적용 방식 |
|:---|:---|:---|
| 토큰 필터 + 의미 검색 | 72건 (82%) | 기본 패턴 |
| 순수 의미 검색 (개인정보 없는 질의) | 8건 (9%) | 토큰 필터 생략 |
| 역할 메타데이터 + 토큰 + 의미 검색 | 2건 (2%) | 종합 단계에서 지원 |

# 5. 평가 설계

## 5.1 평가 지표

| 관점 | 지표 | 측정 방법 |
|:---|:---|:---|
| 토큰 일관성 | 쪼개짐 비율, 합쳐짐 비율 | check_token_consistency.py |
| 검색 정확도 | Hit@k (k=1,3,5,10), Recall@k | eval_retrieval.py |
| 동명이인 검색 | 동명이인 질의 Hit@1 | eval_retrieval.py (유형 필터) |
| 비교 실험 | 토큰 필터 유무에 따른 검색 정확도 차이 | 패턴 A vs 패턴 B 비교 |

## 5.2 데이터 사용 원칙

- 개발·튜닝은 dev+test, 최종 평가는 holdout으로 수행하며 holdout은 최종 평가 전까지 열어보지 않는다.
- 정답 라벨(entities)과 인물 ID(persons_gold)는 채점 및 비교 실험에만 사용한다.

## 5.3 목표 수치 (팀 내 논의 후 확정)

| 지표 | 목표 | 비고 |
|:---|:---|:---|
| 토큰 쪼개짐 비율 | 0% | 필수 조건 |
| Hit@5 | [작성] 이상 | 팀 합의 필요 |
| Recall@10 | [작성] 이상 | 팀 합의 필요 |
