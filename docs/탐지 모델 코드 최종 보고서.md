# 개인정보 탐지기 통합 평가 보고서

작성·평가 정리: 김정하 · 통합일: 2026-10-28

**현재 유력 후보는 팀원 개선 코드 기반 `koelectra_post_kiwi_split_v2`다.** 정하 기존 split은 비교 기준선으로 보존한다. 모델 선정 근거·초기 비교·기존 개선·holdout 관찰·최신 v2 오류 분석을 이 문서에서 관리한다. 실행 방법은 [사용 안내](detector_handoff.md), 프로젝트 목적·평가 설계는 [연구계획서](개인정보%20보호형%20RAG%20챗봇_연구계획서.md)를 따른다.

새 기준 엑셀은 2026-10-28 전달받아 검토했다. 7부의 세 항목은 팀 논의 없이 사용자가 임시로 결정했고 해당 범위의 코드를 개선했다. 나머지 정책은 미결정이며 기존 정답은 바꾸지 않았다. 아래 수치는 각각 명시된 코드·데이터·실행 시점의 결과다. 초기 모델 비교와 최신 v2의 점수·시간을 같은 실험으로 섞지 않는다.

## 1. 초기 공개 모델 선정 근거 — 김정하, 2026-10-23

### 1. 선정 목적과 결론

이번 실험에서는 금융 문서에 포함된 개인정보를 토큰 분류 모델로 탐지하고, 기존 규칙 기반 탐지 결과와 비교한다. 기준 모델은 `BCCard/MoAI-Privacy-Filter-INT8`이며, 추가 모델로 `1T/veil-pii-ko-lite`와 `atonlee/koelectra-ko-pii-ner`를 선정했다.

선정할 때 가장 중요하게 본 것은 우리 평가 라벨과의 대응, CPU 실행 가능성, 구현에 필요한 작업량이다. 이름·전화번호·이메일·주소뿐 아니라 주민등록번호·계좌번호·카드번호도 각각 구분할 수 있어야 한다. 번호 세 종류를 한 라벨로 출력하는 모델은 별도 규칙을 덧붙여야 하므로 이번 우선 비교 대상에서 제외했다.

작성 당시에는 후보 선정 단계였으며 dev 정확도와 처리시간을 측정하기 전이었다. 아래 사양은 당시 확인한 공개 모델 카드를 바탕으로 정리했다. Veil을 먼저 구현하기로 한 것은 실행 준비와 과제 적합성을 고려한 판단이며, 성능이 가장 높다고 확정한 의미는 아니다.

### 3. 기준 모델: MoAI-Privacy-Filter-INT8

MoAI INT8은 한국어와 영어 개인정보 탐지를 위한 ONNX 모델이다. 부모 모델을 INT8로 양자화했으며, CPU 실행을 전제로 제공된다. 학습 데이터는 BC카드의 privacy-filter-openpii-masking 계열로, 공개 PII 데이터와 한국어·영어 합성 시나리오를 포함한다.[1]

우리 평가에 필요한 7종을 별도 라벨로 지원한다. 현재 카드에는 29종, BIOES 클래스 117개로 명시되어 있다. 이전 자료의 라벨 수와 차이가 있으므로 구현에서는 실제 내려받은 버전의 `config.json`을 기준으로 확정한다.

주의할 점은 일반적인 Transformers 토큰 분류 모델과 실행 방법이 다르다는 것이다. 이 저장소에는 PyTorch 가중치가 없으며 ONNX 출력도 완성된 개체가 아닌 logits다. 공식 검증 경로는 BIOES 제약 Viterbi 디코딩과 공백 경계 보정을 거친다. 토큰별 argmax로 대체한 결과를 공식 경로와 동일하다고 볼 수 없다. 1024토큰을 넘는 문서는 분할과 결과 병합이 필요하다.[1]

이 모델은 프로젝트의 기준점으로 사용한다. 추가 모델이 기준 모델보다 가볍게 실행되는지, 정확한 개인정보 경계와 종류를 어느 정도 유지하는지 확인한다.

### 4. 추가 모델 1: Veil

Veil은 KoELECTRA-base 기반의 한국어 개인정보 토큰 분류 모델이다. INT8 ONNX와 실행 코드가 함께 제공되며, 결과를 원문 문자 위치로 반환한다. 공개 실행 코드에는 BIOES 제약 디코딩, 조사 제거, 긴 입력을 위한 창 분할 기능이 포함되어 있다. 우리 평가 코드와 연결할 때 필요한 작업이 비교적 명확하다는 점을 우선 선정 이유로 보았다.[2]

학습에는 BC카드 데이터와 한국어 합성·스트레스 데이터 등이 사용되었다. 기준 모델과 데이터 계열이 일부 겹치므로, 두 모델을 완전히 독립적인 학습 데이터로 만든 비교군이라고 설명하지 않는다.

가장 먼저 확인할 약점은 띄어쓰기 변형이다. 제작자 실험에서는 글자 사이에 공백을 넣은 입력에서 성능이 크게 떨어졌고, 번호의 구분자를 없앴을 때도 성능 하락이 있었다. 우리 데이터의 띄어 쓴 이름과 완전히 같은 실험 조건은 아니지만, `spaced_name`과 전화번호 표기 변형을 별도로 점검할 근거가 된다. 실행 코드의 주소 병합 옵션도 결과에 영향을 주므로 설정값을 기록해야 한다.[2]

Veil은 7종 라벨 대응, BIOES 방식, CPU 실행 코드 제공이라는 조건을 함께 충족한다. 따라서 세 모델 중 먼저 연결해 공통 실행 흐름을 확인할 대상으로 선정했다.

### 5. 추가 모델 2: KoELECTRA

`atonlee/koelectra-ko-pii-ner`는 KoELECTRA-small 기반 모델이다. 약 14M 파라미터로 구성되며, 약 14.7MB의 INT8 ONNX 파일도 제공한다. 금융 PII 데이터와 한국어 PII 데이터, 별도로 작성한 식별자 변형·미끼 사례를 학습에 사용했다고 설명한다.[3]

이 모델을 선정한 이유는 작은 모델에서도 필요한 7종을 직접 구분할 수 있기 때문이다. Veil과 함께 비교하면 경량화에 따른 정확도와 처리시간의 차이를 확인할 수 있다. 다만 크기가 작다는 이유만으로 가장 빠르거나 정확도가 낮다고 미리 결론 내리지는 않는다.

태깅은 BIO 방식이다. 서브워드 단위 출력을 이어 붙여 원문 기준 개체로 복원해야 하며, 이름 라벨이 `PERSON`이 아닌 `NAME`이라는 점에도 주의해야 한다. 주소는 건물번호 등이 포함된 `ADDRESS`와 장소를 나타내는 `PLACE`가 구분된다.[3]

보고서에는 BIO와 BIOES의 차이를 명시한다. 과제에서 모든 추가 모델에 BIOES를 엄격히 요구한다면 이 모델의 비교 허용 여부를 확인해야 한다. 출력 span 형식을 통일하는 것만으로 모델의 학습 태깅 방식이 바뀌지는 않는다.

`FRN`, `VIRTUAL_CARD_NUMBER`, `PLACE`처럼 유사한 라벨을 임의로 합치지 않는다. 추가 매핑이 필요하면 근거와 적용 범위를 먼저 기록한다. 모델이 처음부터 잘못 분류한 결과를 정답 정보를 이용해 고치는 일도 없어야 한다.

## 2. 초기 단독·조합 성능 비교 — 정하 초기 실험

### 초기 단독 모델 비교 참고

아래는 조합 후처리 개선 전의 고정된 비교 결과다. 모델별 조합·라벨·일관성 상세 표는 아래 조합 비교에 수록한다.

| 단독 탐지기 | dev strict F1 / mask_rec | test strict F1 / mask_rec |
|---|---|---|
| rule_kiwi | 0.999 / 1.000 | 0.986 / 0.990 |
| veil | 0.941 / 0.994 | 0.943 / 0.991 |
| koelectra | 0.908 / 0.993 | 0.877 / 0.985 |
| koelectra_post | 0.933 / 0.993 | 0.898 / 0.985 |
| moai | 0.842 / 0.919 | 0.820 / 0.903 |

초기 rule_kiwi의 test 이름 partial 재현율은 0.959로 dev보다 낮았다. 모델이 규칙의 이름 미탐을 보충하는 것이 조합 실험의 근거였다. 초기 조합 6종의 3회 반복 결과는 Jaccard 1.000이지만 최신 후처리의 반복 검증을 뜻하지 않는다.

같은 세션 dev 반복 속도 기록은 rule_kiwi 약 1.1ms, KoELECTRA post 7.5ms, 개선 전 post 조합 9.2ms, Veil 54.5ms, Veil 조합 56.3ms다. rule_kiwi의 이전 11~13ms는 첫 로딩이 섞인 것으로 보인다. 최신 결과의 별도 실행 시간과 섞어 순위를 매기지 않는다.


기준: dev 100건(정답 548개), test 200건(정답 1,165개). 기존 저장 예측을 채점한 결과입니다. **선정 결론은 팀이 정합니다.** 초기 비교 당시의 평가 기록이다. 이후 test도 반복 검토했으므로 현재는 회귀 확인 자료로 해석한다.

- **union:** 이름·주소·번호류 모두 규칙과 모델을 합칩니다. 겹치면 규칙 구간이 우선입니다.
- **split:** 이름·주소는 합치고, 전화·이메일·주민·계좌·카드는 규칙 결과만 씁니다.
- 전체 표의 P/R/F1은 **strict**(라벨·시작·끝 일치), 라벨 표의 P/R은 **partial**(라벨이 같고 구간이 겹치면 인정)입니다. mask_rec은 정답 개인정보 글자 중 가린 비율입니다.

## 3. 정하 기존 split — v6 + fmt_v1

### 1. 탐지 구조·평가 조건

규칙(rule_kiwi)과 KoELECTRA post를 합치며 겹치면 규칙을 우선한다. split은 전화·이메일·주민번호·계좌·카드를 규칙만 사용하고 이름·주소는 합친다. KoELECTRA는 저장소의 INT8 ONNX를 사용하며 재학습하지 않았다. post의 기본 단계는 이름 줄바꿈 분리다. 조합에서 성+직함·문맥·서식 조건을 추가한다.

평가는 합성 데이터의 원문 글자 위치 `[start, end)`와 7종 라벨을 사용한다. organization은 평가에서 제외한다. 정답 인물 목록을 이름 사전으로 쓰지 않았다. dev/test 정답은 합의 기준과 충돌하지 않아 수정하지 않았다. CPU 추론 스레드는 intra-op 2 / inter-op 1이며 모델 로딩·워밍업을 제외한 문서별 시간을 기록한다.

| 지표 | 의미 |
|---|---|
| strict | 라벨·시작·끝이 모두 같아야 정답 |
| partial | 같은 라벨로 구간이 겹치면 1:1 매칭하여 인정 |
| P / R / F1 | 정밀도 / 재현율 / 조화평균 |
| mask_rec | 정답 글자 중 예측 구간으로 가려진 비율. 과도한 마스킹도 높은 값이 될 수 있음 |
| 일관성 | 반복 예측 간 일치도. 정답률과 별개 |

재현율·mask_rec을 우선 확인하고 오탐·정밀도도 함께 본다. 운영 정밀도 하한선과 최종 탐지기 선택은 팀 결정이다. 아래 수치는 정하 기존 split에 대한 평가이며 팀 최종 선정 결과가 아니다.

### 2. 개인정보 판정 기준

아래 기준은 `dev`/`test` 정답과 탐지 결과를 해석하는 팀 기준입니다. 먼저 정답 라벨을 이 기준으로 확인하고, 그다음 같은 기준으로 예측을 채점합니다. 탐지 결과가 정답에 없는 구간을 잡으면 오탐(FP), 정답 구간을 놓치면 미탐(FN)입니다. 라벨이나 시작·끝 위치까지 다르면 `strict` 채점에서는 FP와 FN이 함께 생길 수 있습니다. 같은 라벨의 구간이 겹치면 `partial` 채점에서는 탐지한 것으로 봅니다.

| 대상 | 판정 | 예시와 경계 |
|---|---|---|
| 성 한 글자 + 직함 | 제외 | `허 부장`, `남 부장`의 성 한 글자는 `person` 정답이 아님. 탐지하면 오탐. `허민수 부장`처럼 전체 이름이 있으면 이름 부분은 탐지 |
| 내선번호 | 제외 | `내선 7999`의 `7999`는 `phone_number` 정답이 아님. `내선`의 `내`를 이름·주소로 탐지해도 오탐 |
| 대표번호 | 제외 | `대표번호 1599-0000`, 명시된 고객센터·콜센터 번호 등 공용 연락처는 정답이 아님. 지역번호가 붙어도 **대표번호로 명시되면 제외** |
| 지점명 | 제외 | `여의도 지점` 또는 `여의도지점`은 `address`·`person` 정답이 아님. 별도로 적힌 실제 도로명 주소는 기존 주소 기준 적용 |
| 지역번호가 붙은 전체 전화번호 | 포함 | `02-3961-1452`, `031-123-4567`처럼 `02`/지역번호와 가입자 번호가 모두 있으면 `phone_number` 정답. 집 전화일 가능성을 고려해 개인 소유 여부가 불명확해도 포함하며, 위의 **명시적 대표번호** 예외가 우선 |

`070`은 지역번호가 아니므로 위 항목만으로 포함 여부를 결정하지 않습니다. `02` 같은 지역번호 **두세 자리만 단독으로** 나온 것은 전화번호 정답이 아닙니다. 회사·지점 이름 자체가 아닌 실제 사람 이름, 휴대전화 및 나머지 개인정보 유형은 기존 정답 기준을 따릅니다.

번호 구분 참고: [방송통신위원회 번호 제도 연구](https://www.kcc.go.kr/download.do?fileSeq=32037)는 `02`와 광역 지역번호를 구분하고 `070`을 인터넷전화 식별번호로 설명합니다. 개인정보 포함·제외 판정 자체는 위 팀 기준입니다.

회사명·상품명은 순수 오탐 35건 중 27건(77.1%)이다. 오탐 출처는 모델 추가 34건, 규칙 1건(`고객명`)이다. 최신 재실행의 오류 분포는 기존 v6 기록과 같다.

#### 남는 이유

- **다른 고유명사와 사람 구분:** 회사·상품을 모델이 사람으로 분류한다. 명사 또는 고유명사라는 품사 정보만으로 사람인지 결정할 수 없다.
- **Kiwi와 모델의 동시 오류:** 남은 `달래` 5건은 Kiwi도 `NNP`로 분석했다. 동사 분석일 때만 제거하는 현재 조건을 통과한다.
- **규칙 우선 보호의 한계:** `고객명`은 규칙도 이름으로 탐지한다. 규칙과 겹치지 않는 모델 이름만 문맥 검사하므로 이 경우를 막지 못한다.
- **띄어 쓴 이름·호칭 단서:** D0249의 `전 서윤`은 규칙 후보로 생성됐지만 Kiwi가 `전`을 관형사로 분석해 제외했다. 뒤의 공백+`님`도 강한 이름 단서로 인정되지 않아 모델이 `서윤`만 보충했다.

#### 미탐과 경계 오류를 구분해서 읽기

test는 strict TP 1,164 / 예측 1,200 / 정답 1,165로 **strict FP 36, FN 1**이다. 정답과 전혀 겹치지 않는 순수 미탐은 없으며, partial FN은 0이다. FN 1은 `전 서윤`의 성을 놓친 경계 오류다. 따라서 “오류 CSV 36행”을 strict FP+FN 합계로 해석하면 안 된다. `decoy_company_phone` 등의 오탐수는 해당 태그 문서의 모든 라벨을 세므로 전화번호 오탐 8건이라는 뜻도 아니다.

새 합성 문맥 예제는 개선용 48문장과 별도 check 48문장을 준비했다. 개선용에서 43/48문장이 완전히 일치했으며 상품명 오탐 2, 이름 완전 미탐 2, 이름 분리 오류 1문장이 나왔다. 기존 dev/test 점수가 새 문맥에서도 유지된다고 단정할 수 없다. check는 아직 실행하지 않았다.


### 7. 해석의 한계

- dev 기반 규칙과 후처리이며 test도 반복 평가·오류 문맥 분석에 사용했다. 기존 test는 회귀 확인에 사용하고 독립적인 일반화 근거라고 주장하지 않는다.
- 합성 문서와 반복 템플릿의 점수를 실제 금융 문서 성능으로 일반화하지 않는다. FP32와의 비교 및 제작자 공개 성능 재현은 하지 않았다.
- 성+직함 제외는 팀 판정 기준에 따른 하드 필터다. 문맥·품사 검사도 최종적으로는 통과/제거 규칙이다. 모델·Kiwi·규칙이 함께 틀릴 수 있다. 현재 Span에는 신뢰도가 없으며 임의 가중치를 확률처럼 설명하지 않는다.
- 번호류 split은 규칙 형식 범위에 묶인다. dev/test 지역번호 정답은 02뿐이므로 새 광역 지역번호 지원은 별도 예제에서만 확인했다.
- holdout 최초 결과를 보존했다. 이후 holdout을 보고 개선한 점수는 최초 일반화 점수와 구분하고 기존 dev/test도 재평가한다. **fmt_v1은 holdout 오류를 보고 개선한 결과이며 독립적인 일반화 점수가 아니다.**

### ⑥ Holdout 성능: 개선 전 결과

모델을 holdout에 맞춰 바꾸기 전 **v6 단계**를 비교한다. 최초 추론·채점 완료 후 기록했으며 최초 예측·결과를 보존했다.

| 데이터·단계 | strict P | strict R | strict F1 | partial P | partial R | partial F1 | mask_rec | 평균 ms |
|---|---|---|---|---|---|---|---|---|
| dev v6 | 0.9928 | 1.0000 | 0.9964 | 0.9928 | 1.0000 | 0.9964 | 1.0000 | 10.9 |
| test v6 | 0.9700 | 0.9991 | 0.9844 | 0.9708 | 1.0000 | 0.9852 | 0.9998 | 10.7 |

test→holdout에서 strict F1은 0.9844→0.8509, partial R은 1.0000→0.8618, mask_rec은 0.9998→0.7280으로 낮아졌다. holdout 정답 개인정보 글자의 약 27.2%가 예측 구간으로 덮이지 않았다. 다른 문서 집합·별도 실행의 평균 시간이므로 8.5ms를 속도 개선으로 해석하지 않는다.

저장된 예측을 문서 ID·라벨·시작·끝으로 비교해 개선 전 v6와 **dev/test 모두 예측 구간 집합이 완전히 같음**을 확인했다. strict F1은 dev 0.9964, test 0.9844로 유지됐다. 평균 시간 차이는 별도 실행의 변동으로 보고 개선 속도라고 주장하지 않는다.

#### 검증 및 남은 위험

- `tests/test_rule_formats.py`의 7개 테스트를 실행해 통과했다. 국제전화·주민번호·카드·계좌·주소 변형과 일부 일반 번호 제외를 확인했다.
- **주민번호의 실제 날짜를 검증한 것은 아니다.** fmt_v1은 월·일 범위만 검사하므로 `9002311234567`도 주민번호로 잡힌다. 날짜 유효성 검사와 체크섬 검사는 별개의 과제다.
- **하이픈 계좌는 계좌 단서 없이 허용한다.** `민원번호 2026-0912-3456 접수`를 계좌로 탐지하는 반례를 직접 확인했다. 기존 dev/test에서 회귀가 없어도 새 형식의 민원·접수번호에는 오탐 위험이 있다.
- 번호·주소 재현율은 이번 holdout에서 개선됐지만, 다른 문서 형식까지 안전하다고 단정할 수 없다. 다음 검토는 일반 숫자·하이픈 문서번호의 반례와 남은 이름·주소 오탐을 포함해야 한다.

#### 추가 이름 구조 필터 실험·복구

fmt_v1 이후 nf_v1 구조 필터를 추가한 실험에서는 holdout strict P가 0.9633으로 올랐지만 R이 0.9200, F1이 0.9411, mask_rec이 0.9775로 낮아졌다. 정확한 정답 이름 57개가 제거돼 사용자의 재현율 우선 기준에 따라 이 필터를 폐기했다. 코드와 전용 테스트를 제거한 뒤 새로 생성한 holdout 예측 187문서가 기존 fmt_v1과 완전히 같은 것을 확인했다. 정하 기존 split의 복구 상태는 fmt_v1이며, 복구 확인 자료는 `results/fmt_v1_restored_20261027/`에 보존했다.

#### 평가 해석

fmt_v1 점수는 holdout 오류를 확인한 뒤 맞춘 결과다. **최초 holdout 결과만 개선 전 일반화 확인으로 구분하고, 개선 후 점수를 독립 평가처럼 설명하지 않는다.** 기존 test도 반복 평가·오류 분석에 사용했으므로 회귀 확인으로 해석한다. 최종 운영 후보 선택은 팀이 결정한다.

## 5. 팀원 코드 리뷰 — 현재 유력 후보 split_v2

### 1. 실행 상태와 정책 구분

2026-10-27 `split_v2`를 dev·test·기존 holdout으로 다시 예측하고 채점했다. 세 데이터 모두 앞선 머지 후 평가와 문서별 예측 구간이 완전히 같았다. 앞선 평가의 소스 해시 8개도 현재 파일과 일치함을 확인했다. 이번 작업에서는 탐지 코드를 수정하지 않았다.

| 정책 | 역할 | 번호·주소·이름 처리 요약 |
|---|---|---|
| `split` | 정하 기존 기준선 | 번호 5종은 규칙만 사용. 이름·주소는 규칙 우선으로 모델과 결합. 모델 이름의 문맥 필터와 성+직함 제외 적용 |
| `split_clean` | 팀원 강한 필터 비교안 | 번호는 규칙 기반. 모델 이름에 단어 중간 시작·상품 문맥·품사·짧은 이름 조건 등을 적용하고 최종 공용 번호·지점 등 후처리 |
| `split_v2` | 다음 개선 후보 | 번호·주소·필드 이름 보강 규칙 추가. 형식 검사를 통과한 모델 번호도 허용. 이름 경계·호칭 정리, 외국인 이름 확장, 같은 문서 이름 전파 및 최종 제외 처리 |

정책은 실행 시 하나를 선택한다. `split_v2`는 `split_clean` 전체를 순서대로 실행하는 방식이 아니며 일부 공통 함수 `clean()`을 사용한다. `clean()`에는 070 전화 추가도 있으므로 기존 split의 070 제외와 정책이 다르다. 실제 팀 판정 기준과의 일치 여부는 별도로 확인해야 한다.

### 2. dev·test·holdout 성능

아래는 **팀원 split_v2의 이번 재실행 결과**다. 모델은 KoELECTRA post이며 Veil을 사용하지 않았다.

| 데이터 | 문서 / 정답 | strict P | strict R | strict F1 | partial P | partial R | partial F1 | mask_rec | ms/문서 |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| dev | 100 / 548 | .9874 | 1.0000 | .9937 | .9874 | 1.0000 | .9937 | 1.0000 | 10.0 |
| test | 200 / 1,165 | .9831 | .9983 | .9906 | .9848 | 1.0000 | .9923 | 1.0000 | 9.9 |
| holdout | 187 / 912 | .9881 | .9989 | .9935 | .9892 | 1.0000 | .9945 | 1.0000 | 7.4 |

속도는 이번 실행의 문서별 평균으로 모델 준비 시간을 제외한다. 데이터별 문서 길이 등이 달라 이 표만으로 속도 우열을 판단하지 않는다. 화면의 1.0000은 저장된 반올림 값이며 원시 지표의 무조건적인 완전성을 뜻하지 않는다.

라벨별 **partial 정밀도 / 재현율**:

| 라벨 | dev | test | holdout |
|---|---|---|---|
| person | .9798 / 1.0000 | .9773 / 1.0000 | .9842 / 1.0000 |
| account_number | 1.0000 / 1.0000 | 1.0000 / 1.0000 | .9762 / 1.0000 |
| phone_number·email·address·resident_registration_number·card_number 각각 | 1.0000 / 1.0000 | 1.0000 / 1.0000 | 1.0000 / 1.0000 |

앞선 머지 후 평가에서 정책별 **strict F1**을 비교하면 다음과 같다. 그 평가의 코드와 현재 코드가 동일하고 split_v2 재실행 예측도 동일함을 확인했다.

| 정책 | dev | test | holdout |
|---|---:|---:|---:|
| 기존 split | .9964 | .9844 | .9542 |
| split_clean | 1.0000 | 1.0000 | .9535 |
| split_v2 | .9937 | .9906 | .9935 |

`split_clean`은 dev/test 오류가 없지만 holdout 완전 이름 미탐이 33행이다. `시우`, `재원`, `동현` 같은 정답을 놓쳐, 정밀도만 보고 이 정책을 채택하지 않는다. 기존 split의 holdout 완전 미탐은 4행, split_v2는 0행이다.

### 3. 오류 집계 읽는 법

| split_v2 데이터 | 오탐 | 완전 미탐 | 경계 오류 | 라벨 오류 | 오류 CSV 합계 |
|---|---:|---:|---:|---:|---:|
| dev | 7 | 0 | 0 | 0 | 7 |
| test | 18 | 0 | 2 | 0 | 20 |
| holdout | 10 | 0 | 1 | 0 | 11 |

오류 CSV 한 행과 strict FP/FN 합계는 다르다. test strict FN 2개와 holdout strict FN 1개는 경계 오류다. 개인정보를 전혀 찾지 못한 완전 미탐은 세 세트 모두 없지만, 정확한 라벨·경계 기준의 재현율은 test와 holdout에서 1이 아니다.

### 4. dev 오류 분석 — 7행

| 유형 | 행 수 | 대표 사례 | 해석 |
|---|---:|---|---|
| 상품명을 이름으로 탐지 | 2 | D0018 두 곳의 `하린 포인트 카드` → `하린` | 사람과 상품을 구분하지 못함 |
| 접수 경로 표현을 이름으로 탐지 | 5 | D0037·D0041 등의 `접수 경로: 금융감독원 이첩` → `이첩` | 필드 값에 사용된 일반어를 이름으로 받아들임 |

기존 split의 dev 오류는 `하린` 2행·`보안` 2행이었다. v2에서는 `보안` 2행은 없어졌지만 `이첩` 5행이 남아 오탐 합계가 4→7행으로 늘었다. 기존 split에 있는 접수 경로·일반명사 검토를 v2는 같은 방식으로 호출하지 않는다. 따라서 두 정책의 이름 필터가 동일하다고 해석하면 안 된다.

### 5. test 오류 분석 — 20행

| 유형 | 행 수 | 대표 사례 | 원인·검토 지점 |
|---|---:|---|---|
| 상품명 이름 오탐 | 11 | D0143·D0167 등 `하린 포인트 카드` | 상품 문맥을 충분히 구분하지 못함 |
| 접수 경로 이름 오탐 | 7 | D0114 등 `금융감독원 이첩` | dev에서 나타난 필드 문맥 문제가 test에도 반복됨 |
| 이름에 조사 포함 | 2 | D0199 `이은서`→`이은서는`, D0231 `박준서`→`박준서는` | `tidy_name()`의 호칭 보호 조건과 실제 다음 명사의 구분 문제 |

두 경계 오류는 원문이 `이은서는 고객 안내 문자 …`, `박준서는 고객 안내 문자 …`다. 현재 `tidy_name()`은 후보 다음에 `고객`이 있으면 이름의 일부를 잘못 자르지 않도록 조사 제거를 멈춘다. 여기서는 `고객 안내`의 고객이 호칭이 아닌데 보호 조건에 걸려 `는`이 남는다. 해당 문자열을 함수에 직접 넣었을 때도 같은 결과를 확인했다.

기존 split과 비교하면 오탐은 35→18행으로 줄었다. 기존 회사명·동사 오탐은 이 실행에서 사라졌고 `전 서윤` 경계 오류도 남지 않았다. 다만 v2에서는 위 조사 경계 오류 2행이 생겼으므로 기존 test의 모든 개체가 일괄 개선된 것은 아니다.

### 6. holdout 오류 분석 — 11행

| 유형 | 행 수 | 대표 사례 | 원인·검토 지점 |
|---|---:|---|---|
| 일반 표현의 이름 오탐 | 8 | H0032·H0034 등 `정다운 금융 생활`의 `정다운` | 사람 이름과 동일한 형태인 수식 표현을 구분하지 못함 |
| 일반 단어 일부의 이름 오탐 | 1 | H0142 `결제 알림 미수신`의 `미수` | 단어 앞부분이 이름 형태로 남음 |
| 사건번호의 계좌 오탐 | 1 | H0154 `사건 번호: 경찰청 …`의 숫자 | 모델 번호 허용 이후 식별번호 문맥 검토가 부족함 |
| 이름에 조사 포함 | 1 | H0103 `권온유`→`권온유이` | 받침 조건에 의존한 조사 처리와 원문의 비문법적 표기가 충돌 |

H0154의 사건번호 구간은 기본 규칙과 `extra_spans()`에서 모두 생성되지 않았다. v2는 모델 계좌번호에 자릿수·사업자번호 형태 검사를 적용하지만 사건번호 문맥으로 제외하지 않아, 모델 계좌 예측이 남을 수 있는 경로다. 번호 형식만 넓히는 것으로 해결할 문제는 아니다.

H0103 원문은 `심사역 권온유이 조건 안내 완료.`다. `유`에는 받침이 없어 현재 로직은 다음 `이`를 일반적인 조사로 제거하지 않는다. 실제 이름 끝의 `이`를 보존하려는 조건과 관련되므로, `이`를 무조건 자르는 수정은 피해야 한다. 이 표현을 함수에 넣어 `권온유이`가 유지되는 것을 확인했다.

기존 split의 holdout은 이름 오탐55·주소 오탐3·완전 이름 미탐4·이름 경계12행이었다. v2에서는 완전 미탐과 주소 오류가 사라졌고 이름 경계도 1행으로 줄었다. 다만 사건번호 계좌 오탐 1행이 생겼다. 따라서 이름뿐 아니라 모델 번호를 수용하는 변경도 회귀 확인 대상이다.

### 7. 코드 리뷰 결론과 다음 개선 순서

**v2를 개선 후보로 두되, 기존 split을 보존하고 Veil은 추가하지 않는다.** 이름을 삭제하는 방향뿐 아니라 후보 보완·경계 복구가 효과를 냈다. 반면 필드·상품·사건번호 문맥은 더 확인해야 한다. v2에도 단어 목록과 하드 필터가 있으며 모델·Kiwi·정규식의 합의 확률을 사용하는 것은 아니다.

| 우선순위 | 개선할 부분 | 진행 방향 | 반드시 보존할 사례 |
|---|---|---|---|
| 1 | dev에서 반복된 상품·접수 경로 이름 오탐 | 상품·필드의 역할과 품사·호칭 문맥으로 판정. `하린`, `이첩` 자체를 금지하지 않기 | 실제 인명 `하린 씨`, `이첩 씨`, 고객명에 적힌 이름 |
| 2 | 조사와 호칭의 구분 | `고객 안내`의 명사와 `김민수 고객님`의 호칭 구분. 원문 조사 오류 처리 범위 검토 | 실제 이름 끝에 `이`·`아` 등이 포함된 이름 |
| 3 | 모델 번호의 식별번호 혼동 | 모델이 제안한 계좌에도 사건·접수·민원번호 문맥 검사 검토 | 같은 문서에 정상 계좌와 사건번호가 함께 있는 경우 |
| 4 | 일반 표현·단어 조각 이름 오탐 | 수식어·서술어·단어 내부 경계를 검토. `정다운`, `미수`를 이름 금지어로 추가하지 않기 | 실제 사람 `정다운`, `미수`와 일반 표현의 대조 문장 |

이는 개선 **제안**이며 이번 리뷰에서 구현한 내용은 아니다. 먼저 dev 및 새로 작성한 개선용 대조 문장으로 수정하고, 조건 고정 후 기존 test·holdout을 회귀 평가한다. test·holdout 사례를 보고 제안한 변경은 그 자료에 맞춘 개선임을 기록한다. 별도 검증용 check는 조건 고정 전 열지 않는다.
