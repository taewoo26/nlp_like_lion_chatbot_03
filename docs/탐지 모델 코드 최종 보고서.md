# 실전 프로젝트 1 개인 보고서: 개인정보 탐지기 비교와 규칙+모델 조합

작성: 김정하 · 2026-10-26
범위: 내가 직접 구현·실행한 코드와 그 결과 (KoELECTRA 탐지기·후처리, 규칙+모델 조합, 평가·속도 측정). MoAI·LLM은 팀 비교에 참여한 범위만 적었습니다.

## 1. 한눈에 보기

- 금융사 가상 문서에서 개인정보 7종(이름, 전화, 이메일, 주소, 주민번호, 계좌, 카드)을 찾는 탐지기를 방식별로 비교했습니다. 개인정보는 하나 놓치는 쪽이 더 위험하다고 보고 **재현율과 mask_rec을 먼저, 정밀도는 하한선**으로 봤습니다.
- 규칙 기반(rule_kiwi)은 dev에서 거의 만점이었지만 test에서 이름 재현율이 떨어졌습니다(0.997 → 0.959). 그래서 **규칙 구간을 우선하고 모델이 빈 곳을 채우는 조합**을 만들었습니다.
- 조합은 test에서 재현율 0.995~0.999, mask_rec 0.998~1.000으로 규칙 단독(0.973, 0.990)보다 올랐고, 속도는 모델 단독 + 약 1.5~2ms였습니다.
- 번호류를 규칙에만 맡기는 `split` 정책이 `union`보다 정밀도가 높았습니다(dev, test 모두).
- 최종 운영 탐지기는 팀이 정합니다. 이 문서는 후보를 고르기 위한 근거 자료이고, 모든 점수는 합성 데이터 기준입니다.

## 2. 환경과 평가 방법

- macOS, Python 3.13.7, 프로젝트 `.venv`. 운영 환경은 GPU 없는 CPU 서버로 가정하고 CPU로만 측정했습니다(모델 추론 스레드 intra-op 2 / inter-op 1).
- 데이터는 dev 100건(정답 548개), test 200건(정답 1,165개)입니다. 개선은 dev에서만 하고 test는 중간 확인용으로만 썼습니다. holdout은 아직 열지 않았습니다.
- 채점은 매니저가 제공한 `run_compare.py`를 수정 없이 사용했습니다. strict(라벨·위치 모두 일치), partial(겹치면 인정), mask_rec(정답 글자 중 가려진 비율), 일관성(반복 결과의 Jaccard)을 봤습니다.
- 속도는 로딩과 워밍업을 제외하고 토큰화·추론·디코딩 시간을 문서당 ms로 쟀습니다.

지표별 역할은 아래와 같습니다.

| 지표 | 한 줄 설명 | 이 프로젝트에서의 역할 |
|---|---|---|
| 재현율 (R) | 정답 중 찾은 비율 | 높을수록 미탐이 적음 (우선 지표) |
| 정밀도 (P) | 예측 중 맞은 비율 | 높을수록 오탐이 적음 (하한선) |
| partial | 라벨이 같고 구간이 겹치면 정답 | "찾았는지" 확인 |
| strict | 라벨과 시작·끝이 모두 같아야 정답 | "경계까지 정확한지" 확인, 가명처리에서 같은 사람을 같은 토큰으로 묶을 때 중요 |
| F1 | 정밀도와 재현율의 조화평균 | 참고용 요약 점수 |
| mask_rec | 정답 개인정보 글자 중 가려진 비율 | 라벨·경계와 무관하게 "얼마나 가렸는지" (우선 지표) |
| 일관성 | 반복 실행 결과가 같은 정도 | 정확도와는 별개, 재현성 확인 |

### 주요 파일 설명

| 파일 | 하는 일 | 비고 |
|---|---|---|
| `detection/token_cls/koelectra.py` | 글을 토큰으로 나눠 토큰마다 BIO 태그를 예측하고, 태그를 이어 붙여 원문 위치(Span)를 만듭니다. 긴 문서는 510토큰 창을 128토큰 겹치게 잘라 logits를 평균합니다. | 모델은 재학습하지 않았고 저장소의 INT8 ONNX를 그대로 사용 |
| `detection/token_cls/koelectra_post.py` | koelectra 결과에 후처리를 단계별로 붙입니다. 지금은 `split_lines` 하나(이름이 줄바꿈 사이로 합쳐진 것을 분리). | dev 오류를 보고 만든 임시 후처리 |
| `detection/combo.py` | 규칙(rule_kiwi 전체)과 모델 결과를 합칩니다. 겹치면 규칙 구간을 우선하고, 모델은 겹치지 않는 구간만 추가합니다. | 정책 `union`/`split` |
| `eval/make_preds.py` | 탐지기별 예측을 문서당 한 줄 jsonl로 저장합니다. 조합 이름은 `COMBO_NAMES`로 연결했습니다. | 공통 파일이라 팀에 알리고 수정 |
| `eval/speed_summary.py` | 같은 조건에서 연속 실행한 예측의 ms를 평균·중앙값으로 보여줍니다. | 속도 재측정용 |

### 조합 정책

두 정책 모두 이름이 겹치면 규칙 구간을 씁니다. 규칙이 조사·호칭을 뺀 정답 기준에 맞춰져 있기 때문입니다.

| 정책 | 이름·주소 | 번호류(전화·주민·계좌·카드·이메일) |
|---|---|---|
| `union` | 규칙 + 모델 합집합 | 규칙 + 모델 합집합 |
| `split` | 규칙 + 모델 합집합 | **규칙만 사용** |

모델이 대표번호 같은 미끼를 번호로 잘못 잡는 경우가 많아서 `split`을 시험했습니다. 다만 규칙 정규식이 못 잡는 형식(031/070 번호, 공백 구분 카드번호, 다른 자릿수 계좌)은 모델이 있어도 구제하지 못합니다.

## 4. 실험 흐름

1. **단독 탐지기 비교**: 규칙, 규칙+Kiwi, MoAI, Veil, KoELECTRA를 dev 100건에서 비교했습니다. 규칙 기반은 dev 오류를 보며 다듬어 dev 점수가 거의 만점이었습니다.
2. **KoELECTRA 오류 진단**: 정답과 예측을 원문 위치와 BIO 태그로 직접 비교했습니다. D0002에서 `김은영\n\n윤 선영`이 줄바꿈을 건너 하나로 합쳐지는 것을 확인했고, 이를 `split_lines` 후처리로 풀었습니다. (dev strict F1 0.908 → 0.933)
3. **조합 시험**: 규칙의 약점(이름)을 모델이 메우는지, 모델의 약점(대표번호 오탐 등)을 규칙이 막는지 보려고 조합을 만들었습니다. 정책은 dev로 골랐습니다.
4. **test 확인**: dev로 정한 정책을 test 200건에서 3회 반복해 확인했습니다. test 결과를 보고 규칙을 고치지는 않았습니다.
5. **속도 재측정**: 서로 다른 실행의 ms를 비교하면 안 된다는 것을 알게 되어, 같은 세션에서 3회 연속 다시 쟀습니다.

## 5. 결과

### 5.1 단독 탐지기 (strict F1 / mask_rec)

| 시스템 | dev | test |
|---|---|---|
| rule_kiwi | 0.999 / 1.000 | 0.986 / 0.990 |
| veil | 0.941 / 0.994 | 0.943 / 0.991 |
| koelectra | 0.908 / 0.993 | 0.877 / 0.985 |
| koelectra_post | 0.933 / 0.993 | 0.898 / 0.985 |
| moai | 0.842 / 0.919 | 0.820 / 0.903 |

- rule_kiwi는 dev에서 정밀도 1.000이었지만 test에서 이름 재현율이 0.959로 떨어졌습니다(josa_attached 0.992 → 0.912, given 0.933 → 0.841 등). dev를 보고 만든 규칙이라는 점이 test에서 드러났다고 해석합니다.
- veil은 dev와 test가 거의 같아 안정적이었고, koelectra_post는 dev보다 test가 낮았습니다.
- 후처리 효과는 dev(+0.025)와 test(+0.021) 모두 비슷했습니다. 다만 test에서 partial F1은 후처리 후 오히려 내려갔습니다(0.952 → 0.942). 줄바꿈으로 나눈 조각이 정답과 겹치지 않으면 오탐으로 드러나기 때문으로 추정합니다.

### 5.2 규칙+모델 조합 (test 200건, 3회 중 run1)

| 조합 | strict P | strict R | strict F1 | mask_rec |
|---|---:|---:|---:|---:|
| veil_kiwi_split | 0.959 | 0.995 | 0.977 | 0.998 |
| veil_kiwi | 0.943 | 0.995 | 0.968 | 0.998 |
| koelectra_kiwi_split | 0.933 | 0.995 | 0.963 | 0.998 |
| koelectra_kiwi | 0.920 | 0.995 | 0.956 | 0.998 |
| koelectra_post_kiwi_split | 0.912 | 0.999 | 0.954 | 1.000 |
| koelectra_post_kiwi | 0.900 | 0.999 | 0.947 | 1.000 |
| (참고) rule_kiwi 단독 | 0.999 | 0.973 | 0.986 | 0.990 |

- 조합 6종 모두 rule_kiwi 단독보다 재현율과 mask_rec이 높았습니다. 이름을 규칙이 놓친 자리를 모델이 채웠다는 뜻입니다.
- 세 모델 모두 `split`이 `union`보다 정밀도가 높고 재현율은 같았습니다. 대표번호 오탐(decoy_company_phone)은 veil 33→12, koelectra 34→16으로 줄었습니다.
- 재현율·mask_rec이 가장 높은 것은 koelectra_post 조합이고, 정밀도·F1이 가장 높은 것은 veil 조합입니다. 하나를 고르는 일은 정밀도 하한선을 정해야 가능합니다.
- 반면 정밀도는 rule_kiwi 단독보다 낮습니다. 재현율을 얻고 정밀도를 내준 교환입니다.
- dev에서는 조합이 rule_kiwi 단독보다 정밀도가 낮고 이득이 이름 1개(`은서`)뿐이라, dev 점수만으로는 조합의 가치를 보기 어렵습니다.

### 5.3 속도 (dev 100건, 같은 세션에서 3회 연속, 문서당 ms)

| 시스템 | 평균(3회) | 비고 |
|---|---:|---|
| rule_kiwi | 약 1.1 | run1은 평균 10.6, 중앙값 1.5 |
| koelectra_post | 7.5 | 중앙값 7.6 |
| koelectra_post_kiwi_split | 9.2 | 중앙값 9.1~9.3 |
| koelectra_kiwi_split | 9.4 | |
| veil | 54.5 | 중앙값 56.3 |
| veil_kiwi_split | 56.3 | 중앙값 58.1~58.5 |

- **rule_kiwi의 이전 속도(dev 11.2ms, test 13.2ms)는 Kiwi 첫 로딩 시간이 섞인 값**으로 보입니다. run1은 평균 10.6ms인데 중앙값은 1.5ms이고, run2~3은 1.1ms입니다. 첫 문서 하나가 로딩 시간을 거의 다 가져간 모양입니다. 규칙 기반이 모델보다 느리다고 적은 앞선 기록은 이 점을 고려해 다시 읽어야 합니다.
- 조합 시간은 모델 단독보다 약 1.5~2ms 더 걸렸습니다. 규칙 약 1.1ms에 병합 비용이 더해진 값으로 보입니다.
- 1만 건 환산(단순 평균 유지 가정): koelectra_post_kiwi_split 약 1.5분, veil_kiwi_split 약 9.4분, rule_kiwi 약 11초. 부하를 통제한 분산 측정은 아닙니다.
- 이전 보고서의 서로 다른 실행 간 ms 비교(예: koelectra 14.3ms vs koelectra_kiwi 10.4ms)는 실행 환경이 달라서 생긴 차이로 보여, 속도는 이번 표를 기준으로 써야 합니다.

### 5.4 후보 비교와 선정 기준 (팀 논의용)

내 코드 기준으로 어떤 탐지기가 가장 좋은지 정하려면 기준부터 정해야 했습니다. 이번 과제의 기준은 "개인정보를 놓치지 않는 것"이라서 **재현율과 mask_rec을 우선하고, 정밀도는 하한선으로** 보았습니다. 재현율만 보면 전부 가리는 탐지기(rule 단독: 재현율 0.997, 정밀도 0.624)가 유리해지기 때문에 하한선이 필요합니다.

test 기준 후보 비교입니다(조합은 모두 `split`).

| 후보 | strict P | partial P | strict R | partial R | mask_rec | 문서당 ms | dev→test strict F1 |
|---|---:|---:|---:|---:|---:|---:|---|
| koelectra_post_kiwi_split | 0.912 | 0.913 | 0.999 | 1.000 | 0.9998 | 약 9 | 0.968 → 0.954 |
| koelectra_kiwi_split | 0.933 | 0.935 | 0.995 | 0.997 | 0.9985 | 약 9 | 0.973 → 0.963 |
| veil_kiwi_split | 0.959 | 0.959 | 0.995 | 0.995 | 0.9981 | 약 56 | 0.981 → 0.977 |

참고로 `union` 정책의 koelectra_post_kiwi는 strict P 0.8995, partial P 0.9003으로 0.90 근처에 걸쳐 있어서, 정밀도 하한을 0.90으로 잡으면 `split`이 더 안전합니다. 조합은 strict와 partial 재현율이 거의 같은데(veil은 동일), 단독 KoELECTRA는 strict R 0.910 대 partial R 0.988이었던 것과 대조됩니다. 규칙 구간을 우선하면서 경계 문제가 줄었다고 추정합니다.

- 내 코드(KoELECTRA 계열) 안에서는 재현율과 mask_rec이 가장 높은 쪽이 koelectra_post_kiwi_split입니다. 같은 모델에서는 `split`이 `union`보다 재현율은 같고 정밀도가 높았습니다.
- 다만 재현율 차이는 작습니다. partial 기준으로 1,165개 중 약 6개(0.995 → 1.000) 차이이고, 정밀도 차이(0.912 대 0.959)가 더 큽니다. 몇 개를 더 찾는 대신 오탐이 얼마나 늘어도 괜찮은지가 핵심입니다.
- veil 조합은 dev에서 test로 갈 때 점수 하락이 가장 작았습니다. holdout은 표기 패턴이 더 다양하다고 해서 이 안정성이 중요할 수 있다고 보지만, 확인된 것은 아닙니다.
- 정밀도 하한선에 따라 선택이 달라집니다.

| 정밀도 하한선 | 하한선을 만족하는 후보 중 재현율이 가장 높은 것 |
|---|---|
| 팀 결정 필요 (예: 0.90) | koelectra_post_kiwi_split |
| 팀 결정 필요 (예: 0.95) | veil_kiwi_split |

위 0.90, 0.95는 이해를 돕기 위한 예시이고 **팀이 정한 값이 아닙니다.** 하한선, strict(경계 정확도)를 얼마나 중시할지, 속도 허용 범위를 팀이 정한 뒤 선택합니다. 이 문서는 최종 선택을 하지 않고 선택에 필요한 근거만 정리했습니다.

## 6. KoELECTRA 오류 분석 요약 (koelectra_post 단독, dev 100건, 오류 CSV 58행 기준 / 조합 아님)

| 유형 | 행 수 | 대표 사례 |
|---|---:|---|
| 이름 오탐: 성+직함 | 17 | `허 부장`의 `허`, `남 부장` |
| 이름 오탐: `이첩` | 6 | 금융감독원 접수 경로 문구 |
| 이름 오탐: 일반 단어·상품명 | 5 | `달래`, 상품명 `하린` |
| 이름 오탐: `내선`의 `내`, 갑/을의 `을`, 회사명 `보안` | 8 | D0025, D0043, D0059 |
| 이름 경계 오류 | 9 | `승현아`(조사 포함), `미르보안 권선영`, `조민준 드림` |
| 이름 미탐 | 1 | D0014 `정하은` |
| 번호·주소류 (경계 5, 미탐 2, 오탐 4) | 11 | 계좌 앞자리 누락, 02 전화번호 미탐, 대표번호 조각, 주소 뒤 `로` 포함 |
| 카드→계좌 라벨 오류 | 1 | D0029 |

원인은 코드 구조에서 나옵니다. `bio_to_spans`는 모델이 준 태그를 그대로 옮기고 조사·호칭 제거, 최소 길이, 문맥 필터가 없습니다. 그래서 대부분의 오류는 모델의 태그 선택에서 오고, 번호류 오류는 조합에서 규칙이 대신 맡아 해결됩니다. 이름 오탐은 조합에서도 남습니다(person 정밀도 dev 0.90, test 0.87). 위 표는 조합 전(koelectra_post 단독)의 오류이며, 조합 후 결과는 바로 아래 6-1절에서 따로 분석합니다.

### 6-1. `koelectra_post_kiwi_split` 오류 분석 (dev 100건, 오류 CSV 36행)

분석 대상은 `results/combo_dev/errors_koelectra_post_kiwi_split.csv`입니다. **36행 모두 `person` 오탐**이고, 경계 오류·미탐·번호 및 주소류 오류는 이 CSV에 없습니다.

| 유형 | 행 수 | 대표 사례 |
|---|---:|---|
| 성+직함을 이름으로 탐지 | 17 | D0007 `허 부장님`의 `허`, D0012 `남 부장`, D0035 `이 차장` |
| 민원 접수 문구 `이첩` 또는 그 일부를 이름으로 탐지 | 6 | D0037 `이첩`, D0040 `첩` |
| 일반 단어·상품명을 이름으로 탐지 | 5 | D0007 `달래`, D0018 상품명 `하린`, D0094 `대상` |
| `내선`·갑/을 표시·회사명 일부를 이름으로 탐지 | 8 | D0025 `내`, D0043 `을`, D0059 `보안` |
| **합계** | **36** | **모두 이름 오탐** |

같은 dev 데이터의 `koelectra_post` 단독 오류 CSV(`results/final_dev_final/errors_koelectra_post.csv`, 58행)와 문서 ID·오류 유형·라벨·정답/예측 문자열을 비교하면, **조합의 36행은 단독 모델의 이름 오탐 36행과 모두 같습니다.** 단독 모델에 있던 나머지 22행(이름 경계 9, 이름 미탐 1, 번호·주소류 11, 카드→계좌 라벨 오류 1)은 조합 오류 CSV에 나타나지 않습니다. 규칙 구간 우선 병합과 번호류 `split` 정책을 적용한 결과로 해석할 수 있지만, 각각의 오류가 어느 단계에서 사라졌는지는 이 CSV 비교만으로 단정하지 않습니다.

dev 전체 점수는 strict 재현율 1.000, 정밀도 0.9384이며, 이름의 partial 정밀도는 0.9043입니다. 즉, 이 데이터에서는 놓친 정답 없이 이름 오탐 36개가 남았습니다. 이 분류는 dev 오류를 보고 한 사후 분석이므로 test·holdout의 오류 분포로 일반화할 수 없습니다.

### 6-2. `veil_kiwi_split` 오류 분석 (dev 100건, 오류 CSV 21행)

분석 대상은 `results/combo_dev/errors_veil_kiwi_split.csv`입니다. **21행 모두 오탐**으로, `person` 14행과 `address` 7행입니다. 경계 오류와 미탐은 이 CSV에 없습니다.

| 유형 | 행 수 | 대표 사례 |
|---|---:|---|
| 성+직함의 성을 이름으로 탐지 | 10 | D0007 `허 부장님`의 `허`, D0012 `남 부장`의 `남`, D0039 `강 사원`의 `강` |
| 상품명을 이름으로 탐지 | 3 | D0018 `하린` 2행, D0061 `봄날` |
| 회사명 일부를 이름으로 탐지 | 1 | D0082 `미르보안`의 `미르` |
| 내선번호를 주소로 탐지 | 6 | D0003 `7999`, D0025 `7678`, D0045 `4876` |
| 상호명을 주소로 탐지 | 1 | D0028 `다온편의점` |
| **합계** | **21** | **이름 오탐 14, 주소 오탐 7** |

단독 `veil`은 dev 오류가 57행이었고, 규칙과 합친 `veil_kiwi_split`은 21행입니다. 두 오류 CSV를 행별로 대조한 결과는 다음과 같습니다.

- **사라진 오류 36행:** 이름의 경계 오류 16행과 미탐 6행, 전화번호의 오탐 13행과 미탐 1행이 조합 오류 CSV에는 없습니다. 조합은 이름에서 규칙 구간을 우선하고, 전화번호는 `split` 정책에 따라 규칙 결과만 씁니다. 다만 각 오류가 정확히 어느 단계에서 해결됐는지는 별도로 추적하지 않았습니다.
- **남은 오류 21행:** 단독 `veil`에도 있던 이름 오탐 14행과 주소 오탐 7행이 그대로 남았습니다. `split` 정책에서도 주소는 모델 예측을 함께 사용하므로, 내선번호나 상호명을 주소로 잘못 잡은 사례가 남아 있습니다.

즉, 이 dev 데이터에서는 **놓치는 문제와 전화번호 오류는 줄었지만, 이름·주소를 지나치게 잡는 문제는 남았습니다.**

dev 전체 점수는 strict 재현율 1.000, 정밀도 0.9631입니다. 이름의 partial 정밀도는 0.9605, 주소는 0.8542입니다. 이 분류는 dev 오류를 보고 한 사후 분석이므로 test·holdout의 오류 분포로 일반화할 수 없습니다.

## 7. 한계와 주의

- 모든 점수는 합성 데이터 기준입니다. test 인물의 90%가 dev에도 등장하고 템플릿이 반복되어, 처음 보는 문서에서의 성능은 확인하지 못했습니다. holdout으로 확인할 예정입니다.
- rule_kiwi 규칙과 koelectra_post 후처리는 dev 오류를 보고 만들었습니다. 같은 문구에만 맞는 규칙이 있을 수 있습니다.
- `split`의 번호류는 규칙 정규식 범위(010·02 전화, 4-4-4-4 카드, 3-6-2 계좌)에 묶여 있습니다. dev에 없는 형식은 점수에 드러나지 않았습니다.
- KoELECTRA는 저장소의 INT8 ONNX를 그대로 썼고 FP32와 비교하지 않았습니다. 모델의 학습 데이터와 공개 성능은 직접 재현하지 못했습니다.
- LLM은 dev 기준 기록만 있습니다(HCX-005, strict F1 0.782, mask_rec 0.825, 평균 시간에 재시도 대기 포함). 3회 반복 일관성과 프롬프트 v2의 전체 평가는 하지 않았고 test에서는 돌리지 않았습니다. 외부 API 전송 때문에 운영에는 맞지 않습니다.
- 속도는 한 대의 노트북(CPU)에서 잰 값입니다. 서버 CPU와는 다를 수 있습니다.

## 9. 앞으로 할 일과 팀이 정할 것

- 최종 탐지기 선정: 비교표와 운영 조건(원문 외부 전송 불가, CPU, 라이선스)을 보고 팀이 정합니다. 정밀도 하한선을 몇으로 둘지 먼저 정해야 합니다.
- holdout: 선정한 탐지기를 수정 없이 먼저 평가해 기록한 뒤 오류 분석과 개선을 하고, 개선 후 dev/test도 다시 확인합니다. 시점은 팀과 정합니다.
- 성+직함 오탐(17행)을 줄이는 `drop_surname_title` 후처리는 제안만 했고 실행 결과는 아직 없습니다. 멘토 의견상 `김 과장`은 개인정보로 보기 어렵지만, 운영 기준이 다를 수 있어 적용 여부는 팀이 정합니다.
- 일반화 점검: 031/070 번호, 공백 구분 카드번호, 다른 자릿수 계좌, "번길" 주소를 직접 만든 문장으로 테스트합니다.
- rule_kiwi의 이전 속도 기록을 위 재측정 값으로 정정합니다.
