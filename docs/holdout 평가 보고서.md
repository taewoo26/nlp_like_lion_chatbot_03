# Holdout 평가 보고서

작성: 김정하 · 2026-10-27 · 평가 대상: `koelectra_post_kiwi_split`

**목적:** 캠프파이어 안내의 2부 산출물 **⑤ 데이터 관찰 → ⑥ 개선 전 성능 → ⑦ 오류 분석 → ⑧ 개선·재확인**을 한 문서에서 확인한다. 팀 판정 기준·dev/test 분석은 [탐지 모델 코드 최종 보고서](탐지%20모델%20코드%20최종%20보고서.md), 실행 방법은 [사용 안내](detector_handoff.md)를 따른다. 이번 평가는 정하 후보 기준이며 팀 전체의 최종 운영 탐지기 확정과 별개다.

## ⑤ Holdout 데이터 관찰: dev/test와 무엇이 다른가

직접 JSONL 정답·메타데이터를 집계했다. 아래 개체 수는 **정답 개체 수**, 어려운 사례 태그는 **태그가 붙은 문서 수**이며 서로 다른 단위다. 모든 데이터는 합성 자료다. 대표 사례의 식별번호와 상세 주소는 공개 문서에서 일부 가렸으며, 원문은 로컬 오류 CSV로 확인한다. 데이터 라벨은 바꾸지 않았다.

| 구분 | dev | test | holdout |
|---|---|---|---|
| 문서 | 100 | 200 | 187 |
| 정답 개체 | 548 | 1165 | 912 |
| 문서 유형 | 14 | 14 | 20 |
| 개인정보 없는 문서 | 18 | 32 | 14 |

## ⑥ Holdout 성능: 개선 전 결과

모델을 holdout에 맞춰 바꾸기 전 **v6 단계**를 비교한다. 최초 추론·채점 완료 후 기록했으며 최초 예측·결과를 보존했다.

| 데이터·단계 | strict P | strict R | strict F1 | partial P | partial R | partial F1 | mask_rec | 평균 ms |
|---|---|---|---|---|---|---|---|---|
| dev v6 | 0.9928 | 1.0000 | 0.9964 | 0.9928 | 1.0000 | 0.9964 | 1.0000 | 10.9 |
| test v6 | 0.9700 | 0.9991 | 0.9844 | 0.9708 | 1.0000 | 0.9852 | 0.9998 | 10.7 |
| holdout 최초 v6 | 0.8740 | 0.8289 | 0.8509 | 0.9087 | 0.8618 | 0.8846 | 0.7280 | 8.5 |

test→holdout에서 strict F1은 0.9844→0.8509, partial R은 1.0000→0.8618, mask_rec은 0.9998→0.7280으로 낮아졌다. holdout 정답 개인정보 글자의 약 27.2%가 예측 구간으로 덮이지 않았다. 다른 문서 집합·별도 실행의 평균 시간이므로 8.5ms를 속도 개선으로 해석하지 않는다.

## ⑧ Holdout 개선 내역과 회귀 확인

### fmt_v1 변경 내용

`detection/rule/detector.py`의 번호·주소 규칙을 확대했다. KoELECTRA 모델·이름 후처리를 새로 학습하거나 변경한 개선이 아니다.

| 대상 | 변경 |
|---|---|
| 전화 | `+82` 국제번호 형식 추가. 계좌보다 먼저 검사해 `010-1234-5678`이 확장 계좌 패턴에 들어가지 않도록 함 |
| 주민번호 | 하이픈·공백·구분자 없는 형식 지원. 첫 뒷자리 1~8, 월 1~12·일 1~31 범위 검사. 앞에 계좌·은행 단서가 있으면 주민번호에서 제외 |
| 카드 | 4자리씩 하이픈·공백으로 구분한 형식과 16자리 연속 숫자 지원 |
| 계좌 | 기존 3-6-2 외 여러 하이픈 그룹과 11~14자리 연속 숫자 지원. 연속 숫자는 앞에 계좌·은행 단서가 있어야 허용. 전화 모양 하이픈 번호는 제외 |
| 주소 | 시도 축약형, 도로명·지번, 동·호·층과 일부 건물명·괄호 표기 확대 |

체크섬 검사는 적용하지 않았다. 합성 번호가 유효한 체크섬을 갖는지 확인하지 않은 상태이기 때문이다. `070`은 여전히 탐지 대상 전화 규칙에 포함하지 않았고, 포함 여부는 팀 확인 사항이다.

저장된 예측을 문서 ID·라벨·시작·끝으로 비교해 개선 전 v6와 **dev/test 모두 예측 구간 집합이 완전히 같음**을 확인했다. strict F1은 dev 0.9964, test 0.9844로 유지됐다. 평균 시간 차이는 별도 실행의 변동으로 보고 개선 속도라고 주장하지 않는다.

### 검증 및 남은 위험

- `tests/test_rule_formats.py`의 7개 테스트를 실행해 통과했다. 국제전화·주민번호·카드·계좌·주소 변형과 일부 일반 번호 제외를 확인했다.
- **주민번호의 실제 날짜를 검증한 것은 아니다.** 현재 월·일 범위만 검사하므로 `9002311234567`도 주민번호로 잡힌다. 날짜 유효성 검사와 체크섬 검사는 별개의 과제다.
- **하이픈 계좌는 계좌 단서 없이 허용한다.** `민원번호 2026-0912-3456 접수`를 계좌로 탐지하는 반례를 직접 확인했다. 기존 dev/test에서 회귀가 없어도 새 형식의 민원·접수번호에는 오탐 위험이 있다.
- 번호·주소 재현율은 이번 holdout에서 개선됐지만, 다른 문서 형식까지 안전하다고 단정할 수 없다. 다음 검토는 일반 숫자·하이픈 문서번호의 반례와 남은 이름·주소 오탐을 포함해야 한다.

### 추가 이름 구조 필터 실험·복구

fmt_v1 이후 nf_v1 구조 필터를 추가한 실험에서는 holdout strict P가 0.9633으로 올랐지만 R이 0.9200, F1이 0.9411, mask_rec이 0.9775로 낮아졌다. 정확한 정답 이름 57개가 제거돼 사용자의 재현율 우선 기준에 따라 이 필터를 폐기했다. 코드와 전용 테스트를 제거한 뒤 새로 생성한 holdout 예측 187문서가 기존 fmt_v1과 완전히 같은 것을 확인했다. 현재 적용 상태는 fmt_v1이며, 복구 확인 자료는 `results/fmt_v1_restored_20261027/`에 보존했다.

### 평가 해석

fmt_v1 점수는 holdout 오류를 확인한 뒤 맞춘 결과다. **최초 holdout 결과만 개선 전 일반화 확인으로 구분하고, 개선 후 점수를 독립 평가처럼 설명하지 않는다.** 기존 test도 반복 평가·오류 분석에 사용했으므로 회귀 확인으로 해석한다. 최종 운영 후보 선택은 팀이 결정한다.
