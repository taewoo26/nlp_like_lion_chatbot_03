# **1\. 연구 배경 및 비즈니스 니즈**

금융사는 상담 기록, 민원, 업무 메일, 회의록 같은 사내 문서를 LLM 기반 검색·요약 서비스에 활용하려는 수요가 크다. 그러나 이 문서들에는 고객 실명, 휴대전화, 주민등록번호, 계좌·카드번호가 섞여 있어 그대로 활용할 수 없다.  
탐지에서 놓친 개인정보는 벡터 DB, LLM 로그, 외부 API로 그대로 흘러가며, 한 번 적재되면 되돌리기 어렵다. 반대로 모든 값을 단순 마스킹(\*\*\*)하면 "같은 사람이 어느 문서에 나오는가"라는 연결 정보까지 사라져 검색 자체가 불가능해진다. 본 과제가 **단순 마스킹이 아닌 결정적 토큰 기반 가명처리를 지향**하는 이유다.

**실전 1의 위치.** 개인정보 탐지는 전체 파이프라인(탐지 → 가명처리 → 벡터 DB 적재 → 검색 → 출력 재검사 → 권한별 복원)의 첫 관문이다. 여기서 놓친 개인정보는 이후 어떤 단계에서도 복구되지 않으며, 탐지 범위가 정확해야 실전 2에서 '윤 선영'과 '윤선영'이 같은 토큰으로 묶인다. 즉 탐지 품질은 전체 시스템 품질의 상한선이다.

# **2\. AI 문제 정의**

## **2.1 과제의 정형화**

본 과제는 비정형 한국어 문서에서 개인정보 구간(span)을 찾아 유형 라벨을 부여하는 개체명 인식(NER), 즉 시퀀스 라벨링 문제로 정의한다.

* **입력:** 가상 금융사 사내 문서 텍스트  
* **출력:** (라벨, 시작 위치, 끝 위치)의 집합. 위치는 원문 글자 기준 \[start, end) 반열린 구간  
* **라벨(7종):** person, phone\_number, email, address, resident\_registration\_number, account\_number, card\_number

## **2.2 두 종류의 하위 문제**

탐지 대상은 성격이 다른 두 문제로 나뉜다. 이 구분이 탐지 방식 비교와 조합(하이브리드) 검토의 근거가 된다.

| 구분 | 대상 라벨 | 문제 성격 |
| :---- | :---- | :---- |
| 정형 개인정보 | 전화번호, 주민등록번호, 계좌번호, 카드번호, 이메일 | 형식이 정해진 패턴 매칭 문제. 형식 변형과 미끼 번호 구분이 핵심 |
| 비정형 개인정보 | 이름, 주소 | 문맥을 봐야 하는 언어 이해 문제. 경계 결정과 일반어 구분이 핵심 |

## **2.3 문제를 어렵게 만드는 요인 (데이터 관찰 근거)**

| 요인 | 내용 | 데이터 근거 (dev) |
| :---- | :---- | :---- |
| 클래스 불균형 | 이름이 전체 개체의 약 62%로 압도적, 번호류는 각 16\~20개 수준 | dev 548개 중 person 340개 |
| 한국어 조사·호칭 | 이름 뒤에 조사·호칭이 붙어도 정답 범위는 이름까지만 | 윤선영은, 오서연님, 승현아 |
| 띄어쓰기·이름만 표기 | 같은 인물이 여러 표기로 등장 | spaced 27개, given 15개 |
| 형식 변형 | 같은 유형이 여러 형식으로 등장 | 전화번호 형식 7가지 |
| 비대상(미끼) | 개인정보처럼 보이지만 라벨이 없는 표현 | 1599-0000, 민원번호, 허 부장, 한결같이 |
| 일반화 위험 | 템플릿 기반 합성 데이터로 dev·test가 크게 겹침 | test 인물의 90%가 dev에도 등장 |

## **2.4 비대칭 비용과 운영 제약**

일반적인 NER은 F1 하나로 성능을 비교하지만, 본 문제에서는 개인정보 하나를 놓치는 비용(유출)이 하나를 더 가리는 비용(검색 품질 저하)보다 훨씬 크다. 따라서 재현율과 마스킹 재현율(mask\_rec)을 우선 지표로 두되, 과도한 오탐이 검색 품질을 해치지 않는지 정밀도도 함께 본다.  
또한 운영 환경을 고려해 다음 제약을 문제 정의에 포함한다.

* **속도:** GPU 없는 CPU 서버 기준 처리 시간  
* **일관성:** 같은 입력에 같은 출력. 가명처리 토큰이 흔들리면 검색이 깨짐  
* **데이터 반출:** 개인정보를 찾기 위해 원문을 외부 LLM에 보내는 모순. 실험은 가상 데이터라 허용되나 운영 적용 가능성은 별도 검토

# **4\. 해결 접근**

## **4.1 비교 대상 탐지 방식과 가설**

| 방식 | 구성 | 예상 강점 | 예상 약점 |
| :---- | :---- | :---- | :---- |
| 규칙 기반 | 정규식 \+ 형태소 분석기(Kiwi) \+ 호칭·성씨 규칙 | 빠르고 결과가 항상 같음, 번호류에 강함 | 처음 보는 이름 표현, 이름만 부르는 경우 |
| 토큰 분류 모델 | BIOES 한국어 NER 모델 (기준 모델 \+ 추가 모델 1개 이상) | 문맥 기반 이름 탐지, CPU 운영 가능 | 모델 라벨 체계와 7종 불일치, 경계 오류 |
| LLM | 클라우드 LLM API (프롬프트 기반) | 어려운 사례에 유연하게 대응 | 느림·비용, 반복 실행 시 결과 흔들림, 원문 반출 |

## **4.2 공통 구성 요소**

* **라벨 가이드라인:** 라벨별 포함·제외·경계 기준과 비대상 목록을 팀 공통 기준으로 확정  
* **입력 정규화:** 번호 구분자 통일 등은 사본에만 적용하고 원문 위치 매핑을 유지  
* **경계 후처리:** 모든 탐지기 결과에 조사·호칭·괄호 제거 규칙을 공통 적용  
* **조합안:** 방식 간 합집합 또는 라벨별 방식 분담(번호류는 규칙, 이름은 모델 등)을 추가 실험

# **5\. 평가 설계**

## **5.1 평가 지표**

| 관점 | 지표 | 측정 방법 |
| :---- | :---- | :---- |
| 정확도 | strict / partial P·R·F1, mask\_rec, 라벨별 재현율 | run\_compare.py |
| 어려운 사례 | 태그별 재현율(조사, 띄어쓰기, 이름만, 동명이인, 형식 변형), 미끼 문서 오탐 수 | run\_compare.py hard case 표 |
| 속도 | 문서당 처리 시간(ms), 1만 건 처리 예상 시간 | CPU 기준 측정 |
| 일관성 | 3회 반복 실행 평균 Jaccard, 결과 완전 일치 문서 비율 | run\_compare.py 반복 실행 모드 |
| 일반화 | test 대비 holdout 점수 차이 | 최종 평가 시 1회 |

## **5.2 데이터 사용 원칙**

* 개발·튜닝은 dev, 중간 확인은 test, 최종 평가는 holdout으로 수행하며 holdout은 최종 평가 전까지 열어보지 않는다.  
* 이름 사전에 데이터셋 인물 목록(정답)을 사용하지 않는다. 정답을 미리 보는 것과 같아 성능이 과대평가되기 때문이다.

## **5.3 탐지기 선정 기준 (실험 전 확정)**

결과를 보고 기준을 맞추지 않도록 선정 기준을 실험 전에 정해둔다. 아래는 초안이며 팀 논의 후 확정한다.

* **필수 조건:** mask\_rec \[작성: 예 0.95\] 이상, 미끼 문서 오탐 \[작성\] 건 이하  
* **우선 비교:** 필수 조건 통과 방식 중 partial 재현율 → 문서당 처리 시간 → 일관성 순  
* **운영 적합성:** 원문 외부 반출 여부, 비용, 라이선스
