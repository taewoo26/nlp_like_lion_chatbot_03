# 권한 정책 기준 (v0.4)

최종 수정 2026-11-09
근거: 종합 프로젝트 계획서(예상 사용자 Lv0~2, 실명 복원 Lv2 한정, 알 수 없는 문서는 상위 권한만 열람), `docs/doc_type_inventory.csv`(doc_type 33종, 487문서)
정책 저장: 현재 `policy/access_policy.yaml`. 관리자 화면 편집 결정(9절 결정 3)에 따라 **DB 정책 테이블로 옮기며, YAML은 초기값(시드)으로 바뀝니다**(테이블 설계 진행 중).

> 아직 팀 전체 검토 전입니다. 계획서 예시와 달라진 항목은 **[계획서와 차이]**로 표시했습니다. 결정 사항과 변경 이력은 9절에 있습니다.

## 1. 기본 원칙

1. **레벨은 사람(사용자)의 등급입니다.** 문서 쪽에는 "이 문서를 보려면 최소 몇 등급이어야 하는가"(`min_level`)를 정합니다.
2. **권한 판단은 코드가 합니다.** LLM에는 권한 정보를 주지 않으며, 사용자의 레벨은 로그인 인증 단계에서 정해집니다.
3. **검색 전에 거릅니다.** 권한 밖 문서는 후보 단계에서 제외하며, 검색 후 숨기는 방식은 쓰지 않습니다.
4. **기본값은 거부입니다.** 정책에 없는 doc_type은 Lv2 전용으로 처리합니다(holdout2 신규 템플릿 대비, 계획서의 "알 수 없는 문서는 상위 권한만 열람").
5. **열람과 복원은 별개입니다.** 문서를 볼 수 있어도 토큰 상태로 봅니다. 실명 복원은 Lv2만 가능합니다.
6. **계층형입니다.** 상위 레벨은 하위 레벨의 모든 권한을 포함합니다(Lv2 ⊇ Lv1 ⊇ Lv0).

## 2. 레벨 정의

| 레벨 | 대상 사용자 | 열람 가능 문서 | 보이는 형태 | 감사 로그 열람 |
|---|---|---|---|---|
| Lv0 | 일반 조회자(전 직원) | 전 직원 공개 문서(공지·안내·PII 없는 현황) | 토큰 상태 | 불가 |
| Lv1 | 상담원·민원 담당자 | **직원 개인 문서를 제외한 모든 문서** | 토큰 상태 | 불가 |
| Lv2 | 관리자·준법 담당자 | 모든 문서(직원 개인 문서, 미등록 doc_type 포함) | **원문(실명 복원)**, 복원 이력 기록 | 가능 |

정리하면, Lv0은 일부 문서만 보고, Lv1은 직원 개인 문서를 뺀 대부분의 문서를 토큰 상태로 보며, Lv2는 모든 문서를 원문으로 봅니다.

## 3. doc_type의 min_level 판정 기준

위에서부터 차례로 적용하고, **처음 해당하는 규칙**으로 정합니다.

| 순서 | 판정 질문 | 분류 이름 | min_level |
|---|---|---|---|
| 1 | 정책에 등록되지 않은 doc_type인가? | (행 없음) | Lv2 |
| 2 | **직원 개인에 관한** 인사·채용·감사·비용 소명 문서인가? | 직원개인 | Lv2 |
| 3 | 고객 정보(이름·연락처·주소·주민번호·계좌·카드)가 포함되거나 고객 업무 처리 기록인가? (심사·분쟁 포함) | 고객업무 | Lv1 |
| 4 | 직원 간 업무 소통·회의·보고이거나 회사 운영 문서인가? (계약·권한 신청 포함) | 내부업무 | Lv1 |
| 5 | 전 직원 공개용 공지·안내이거나, PII가 없는 내부 현황 집계인가? | 공개 | Lv0 |

판정 질문의 결과는 **분류 이름**으로 정책 표(`category` 컬럼)에 저장합니다. 번호 대신 이름을 쓰므로 값만 봐도 뜻이 보입니다. 질문 1은 정책에 행이 없는 경우라서 저장되는 값이 없습니다. 질문의 **순서**는 새 유형을 사람이 분류할 때 쓰는 절차이고, DB에는 분류 결과만 저장합니다. 분류 이름은 기존 행에서 바꿀 수 없습니다(잘못 분류했다면 삭제 후 다시 추가).

표의 min_level은 각 분류의 **기본 레벨이자 하한**입니다. 관리자는 doc_type별로 레벨을 올릴 수만 있고, 기본 레벨 아래로 내릴 수는 없습니다(9절 결정 8). 예를 들어 회의록(내부업무)은 Lv2로 올릴 수 있지만 Lv0으로 내릴 수는 없고, `직원개인`은 항상 Lv2입니다.

판정 메모
- Lv2 전용 예외는 **직원 개인에 관한 문서**로 최소화했습니다. 가명처리는 이름·번호만 토큰으로 바꾸고 팀명·직급·사건 내용은 남기므로, 직원 개인 문서는 토큰 상태로도 당사자를 알아볼 위험(재식별)이 크기 때문입니다.
- 고객 정보와 고위험 번호(주민·계좌·카드)가 있는 문서도 Lv1에서 볼 수 있습니다. 상담원의 핵심 업무 문서이고 토큰 상태로만 보이기 때문입니다. 원문은 복원 규칙(4절)에서 통제합니다.

## 4. 복원 규칙 (level × label)

| 라벨 | Lv0 | Lv1 | Lv2 |
|---|---|---|---|
| person, phone_number, email, address | none | none | full |
| resident_registration_number, account_number, card_number | none | none | full |

- 복원 모드는 현재 `none` / `full` 두 가지만 사용합니다. 일부만 보여주는 `partial`은 추후 논의합니다.

## 6. 영향 정리

- **계획서와 차이 2건**: 계획서 2절 예상 사용자 항목은 Lv2 조회 대상으로 "인사 발령·계약서·회의록"을 적고 있습니다. 이 정책에서는 인사발령만 Lv2이고 회의록과 용역계약서는 Lv1입니다. 계획서를 고치거나 정책서의 변경 사유로 남겨야 합니다.
- **Lv1 재식별 위험**: Lv1이 고객 심사·분쟁 문서와 회사 운영 문서까지 토큰 상태로 봅니다. 팀명·직급·사건 내용이 남아 있어 당사자를 추정할 수 있는 경우가 있으므로, 최종 리포트의 한계에 적습니다.
- **Lv2 전체 복원**: 고위험 라벨까지 전부 복원되므로 복원 감사 로그와 출력 재검사가 더 중요해집니다.

## 7. 사용자 레벨 부여 기준

1~6절은 "레벨별로 무엇을 볼 수 있는가"이고, 이 절은 "어떤 사용자에게 어느 레벨을 주는가"입니다.

### 7.1 원칙

1. **업무상 필요한 만큼만 줍니다(최소 권한).** 레벨은 그 사람이 업무에 꼭 필요한 문서와 기능을 기준으로 정합니다.
2. **팀(직무)이 주 기준입니다.** 개인별로 따로 정하지 않고, 같은 업무를 하는 사람은 같은 레벨을 받습니다.
3. **직급은 사용하지 않습니다.** 팀장이라는 이유만으로 Lv2를 주면 실명 복원 권한을 가진 사람이 넓어지기 때문입니다. 계획서의 "알 수 없는 문서는 팀장 이상만 열람"은 미등록 doc_type을 Lv2 전용으로 막는 것(1절 원칙 4)으로 반영합니다.
4. **팀을 알 수 없거나 대응표에 없는 팀이면 Lv0**입니다(기본 거부).
5. **여러 팀에 걸친 사람은 주 소속 팀 하나**로 정합니다.

### 7.2 레벨별 업무 필요

| 레벨 | 업무상 필요 |
|---|---|
| Lv0 | 사내 공지·안내만 보면 되는 사람 |
| Lv1 | 고객 응대·처리를 위해 고객·업무 문서를 봐야 하는 사람(실명은 불필요) |
| Lv2 | 인사·감사·준법 업무로 직원 개인 문서와 원문까지 봐야 하는 사람 |

### 7.3 팀 → 레벨 대응표 (초안)

dev/test와 현재 holdout(실전 2 검색 코퍼스) 문서 본문에서 확인한 팀 이름 기준입니다. 정규식으로 찾은 것이라 누락이 있을 수 있습니다. 직원 목록이 확정되면 갱신합니다.
- 참고 범위: 팀·직급 표현만 찾았고, 개인정보와 정답 파일(`*_gold.jsonl`)은 쓰지 않았습니다. 평가 전용인 holdout2는 보지 않습니다.
- 확인 결과: holdout에도 dev/test와 같은 10개 팀만 나오며 새 팀은 없습니다. 데이터에 준법감시·감사 전담 조직은 없습니다.
- 리스크관리팀은 이상거래탐지·피해접수·대출상담 문서에 주로 나오는 고객 사고 처리 조직이라 Lv1로 둡니다(처음 초안의 Lv2 가정을 변경).
- "고객센터"는 카드분실상담·고객정보변경·녹취요약 등 상담 문서와 인사발령에 나오는 **상담 조직**입니다. 다만 133회 중 23회는 "고객센터 1599-…"처럼 대표 연락처 표기라서, 직원 목록을 만들 때 둘을 구분해야 합니다.

| 레벨 | 팀 | 이유 |
|---|---|---|
| Lv2 | 인사팀, 정보보호팀 | 인사팀은 인사발령·채용 문서 담당, 정보보호팀은 개인정보 보호·권한 신청(보안 통제) 담당. 데이터에 준법감시 조직이 없어 **준법 역할은 정보보호팀이 맡는 것으로 가정** |
| Lv1 | 고객보호팀, 채권관리팀, 카드운영팀, 여신심사팀, 리스크관리팀, 고객센터(상담원) | 고객 상담·민원·심사·채권·고객 사고(이상거래·피해 접수) 업무 |
| Lv0 | IT운영팀, 디지털전략팀, 그 외 | 고객 문서가 업무에 필수는 아님 |

### 7.5 저장 방식 (로그인 구현 요구사항)

- 계정 정보에 **`level`(0~2, 필수)**을 저장합니다. 권한 판단의 기준값입니다.
- **`team`(선택)**도 함께 저장합니다. 지금은 기록용이고, 2차 기준(담당 팀)이나 ABAC 전환 때 사용합니다.
- 레벨은 **함수 하나(예: `get_user_level(user)`)를 통해서만** 가져오고, 그 값을 `search_filter(level)`, `restore_mode(level, label)`에 넘깁니다.
- 팀 → 레벨 대응표는 **DB 정책 테이블(팀별 기본 레벨)**에 두고 관리자 화면에서 편집합니다(9절 결정 3). 계정을 만들 때 이 표로 **기본 레벨을 채우고**, 이후 관리자가 사용자별로 바꿀 수 있습니다. 검색할 때는 계정의 `level`만 보므로, 팀 표를 고쳐도 기존 사용자의 레벨은 바뀌지 않습니다.
- (이전 방침: 대응표는 이 문서에만 두고 코드에 넣지 않음. 관리자 화면 편집 결정으로 변경)
- 계정은 PoC에서 시연용 3개뿐이고 부서 이동이 없으므로, 레벨을 직접 저장하는 방식이 가장 단순합니다.

### 7.6 속성 기반(ABAC) 방식으로 바꾸는 조건

ABAC 방식은 계정에 팀만 저장하고, 로그인할 때 팀 → 레벨 규칙으로 레벨을 계산하는 방식입니다.

- **전환 조건**: 2차 기준(사용자 팀 = 문서 담당 팀)을 도입하거나, 계정이 많아져 레벨을 일일이 관리하기 어려워질 때
- **전환 작업**: 팀별 기본 레벨 테이블(9절 결정 3)을 로그인 시 계산에 사용, `get_user_level()` 안쪽을 계산 방식으로 교체(직접 지정 예외 포함), 테스트 추가, 기존 계정의 저장 레벨과 계산 레벨 비교
- **비용을 줄이려면 지금 할 일**: `team` 칸을 미리 두고(7.5), 레벨을 함수 하나로만 가져오며(7.5), 직원 목록의 **팀 이름 표기를 하나로 통일**합니다(예: "고객보호팀"과 "고객 보호팀" 혼용 금지). 가장 큰 변수는 코드가 아니라 팀 이름 데이터 정리입니다.
- 검색·복원·감사 로그 코드는 레벨 숫자만 받으므로 바뀌지 않습니다.

### 7.7 참고 자료

AWS 문서는 AWS 자원(IAM) 권한 관리 기준이며, 이 정책은 같은 원칙을 앱 사용자 권한에 적용한 것입니다.
- [AWS Well-Architected SEC02-BP06 Employ user groups and attributes](https://docs.aws.amazon.com/wellarchitected/latest/security-pillar/sec_identities_groups_attributes.html): 접근하는 자원이 아니라 사용자가 하는 업무로 그룹을 정의하라. 개인별 권한 관리를 피하라.
- [AWS Well-Architected SEC03-BP02 Grant least privilege access](https://docs.aws.amazon.com/wellarchitected/latest/security-pillar/sec_permissions_least_privileges.html): 직무별 역할 매트릭스, 기본 권한 없음, 관리자 권한은 소수의 신뢰할 수 있는 그룹으로 제한, 정기 권한 검토.
- [AWS IAM Identity Center: Attribute-based access control](https://docs.aws.amazon.com/singlesignon/latest/userguide/abac.html): 팀 속성으로 접근을 정하면 팀 이동 시 속성만 바꾸면 됨(7.6의 전환 방식).

## 8. 적용 범위와 한계

이 정책은 **챗봇 사용자(앱)의 권한**만 다룹니다. 서버(AWS EC2)와 DB를 관리하는 사람의 권한은 범위 밖이며, 배포 시 아래를 지켜야 정책의 효과가 유지됩니다.

| 항목 | 내용 |
|---|---|
| 인프라 관리자 | EC2 접속이나 DB 관리자 계정으로는 챗봇을 거치지 않고 `vault.token_map`(실명)과 감사 로그에 접근할 수 있습니다(사실상 Lv2보다 강한 권한). 이 권한은 소수(배포 담당 팀원)로 제한하며, 이들의 접근은 앱 감사 로그에 남지 않습니다. |
| 감사 로그 보호 범위 | "추가만 가능" 제한은 앱 계정(`rag_user`, `vault_user`)에 대한 보호입니다. DB 관리자는 로그를 바꿀 수 있습니다. 더 강한 보호(로그를 서버 밖으로 별도 전송)는 확장 항목입니다. |
| 비밀 값 | HMAC 키·DB 비밀번호·LLM API 키는 Secrets Manager로 관리합니다(계획서). `vault_user` 비밀번호는 복원 모듈만 사용합니다. |
| 네트워크 | DB 포트는 외부에 열지 않고(`127.0.0.1`), 외부에는 HTTPS만 엽니다(계획서). |
| 정책 운영 | 정책은 DB에 두고 관리자 화면에서 편집합니다. 편집할 때마다 정책 버전 번호가 올라가고, 변경 내용은 변경 이력에 남습니다. 로그의 `policy_version`으로 어느 정책으로 판단했는지 추적합니다. 앱은 정책을 캐시해 쓰되, 버전이 바뀌면 다시 읽습니다. |

실서비스 적용 시 추가로 필요한 것(최종 리포트 한계 항목)
- 감사 로그 **보관 기간과 정기 점검**: 개인정보의 안전성 확보조치 기준 제8조(접속기록 보관 및 점검) 참고. 리포트 인용 전 국가법령정보센터 원문 확인 필요.
- 사용자 **레벨 변경 이력** 기록: 같은 기준 제5조(접근 권한의 관리) 참고.
- Lv1의 **재식별 위험**(6절)과 탐지 누락 시 원문 노출 가능성.
