# 권한 정책 기준 (v0.3, 논의 항목 6건 반영)

작성: 정민영 · 2026-11-06
근거: 종합 프로젝트 계획서(예상 사용자 Lv0~2, 실명 복원 Lv2 한정, 알 수 없는 문서는 상위 권한만 열람), `docs/doc_type_inventory.csv`(doc_type 33종, 487문서)

> v0.3 변경: v0.2의 논의 항목 6건을 결정해 반영했습니다(7절). 아직 팀 전체 검토 전이며, 계획서 예시와 달라진 항목은 **[계획서와 차이]**로 표시했습니다.

## 1. 기본 원칙

1. **권한 판단은 코드가 합니다.** LLM에는 권한 정보를 주지 않으며, 레벨은 로그인 인증 단계에서 정해집니다.
2. **검색 전에 거릅니다.** 권한 밖 문서는 후보 단계에서 제외하며, 검색 후 숨기는 방식은 쓰지 않습니다.
3. **기본값은 거부입니다.** 정책에 없는 doc_type은 Lv2 전용으로 처리합니다(holdout2 신규 템플릿 대비).
4. **열람과 복원은 별개입니다.** 문서를 볼 수 있어도 토큰 상태로 봅니다. 실명 복원은 Lv2만 가능합니다.
5. **계층형입니다.** 상위 레벨은 하위 레벨의 모든 권한을 포함합니다(Lv2 ⊇ Lv1 ⊇ Lv0). doc_type마다 `min_level` 하나만 둡니다.

## 2. 레벨 정의

| 레벨 | 대상 사용자 | 열람 가능 문서 | 실명 복원 | 감사 로그 열람 |
|---|---|---|---|---|
| Lv0 | 일반 조회자(전 직원) | 전 직원 공개 문서(공지·안내·PII 없는 현황) | 불가 | 불가 |
| Lv1 | 상담원·민원 담당자 | Lv0 + 고객·업무 처리 문서 | 불가 | 불가 |
| Lv2 | 관리자·준법 담당자 | 전체(인사·감사·계약·심사 문서와 미등록 doc_type 포함) | 가능(복원 이력 기록) | 가능 |

## 3. doc_type의 min_level 판정 기준

위에서부터 차례로 적용하고, **처음 해당하는 규칙**으로 정합니다.

| 순서 | 판정 질문 | min_level |
|---|---|---|
| 1 | 정책에 등록되지 않은 doc_type인가? | Lv2 |
| 2 | 인사·채용·감사·계약·내부통제·준법 검토·보안 통제 문서이거나, **내부 심사 판단**이 담긴 문서인가? (개인정보가 적어도 내용 자체가 민감) | Lv2 |
| 3 | 고객 정보(이름·연락처·주소·주민번호·계좌·카드)가 포함되거나 고객 업무 처리 기록인가? | Lv1 |
| 4 | 직원 간 업무 소통·회의·보고 문서인가? | Lv1 |
| 5 | 전 직원 공개용 공지·안내이거나, **PII가 없는 내부 현황 집계**인가? | Lv0 |

판정 메모
- 고위험 라벨(주민·계좌·카드) 포함 여부만으로 Lv2로 올리지 않습니다. 상담원(Lv1)의 핵심 업무 문서이고 토큰 상태로만 보이기 때문입니다. 고위험 라벨은 복원 규칙(4절)에서 통제합니다.
- 인사·감사·계약 문서는 개인정보가 없어도 Lv2입니다.
- 규칙 2의 "내부 심사 판단"은 한도심사결과·카드발급심사에 적용되었고, 이후 유사한 심사·평가 문서가 추가될 때의 기준이 됩니다.

## 4. 복원 규칙 (level × label)

| 라벨 | Lv0 | Lv1 | Lv2 |
|---|---|---|---|
| person, phone_number, email, address | none | none | full |
| resident_registration_number, account_number, card_number | none | none | full |

- 복원 모드는 현재 `none` / `full` 두 가지만 사용합니다. 일부만 보여주는 `partial`은 추후 다시 논의합니다(7절).
- 모든 복원은 `audit.restore_log`에 사용자·시각·토큰·라벨·모드·정책 버전으로 기록하며, 원문은 남기지 않습니다.

## 6. 영향 정리

- **회의록 Lv1**: 계획서 2절 예상 사용자 항목은 회의록을 Lv2 조회 대상으로 적고 있어, 계획서 수정 또는 정책서에 변경 사유를 남기는 것이 필요합니다.
- **민원현황 Lv0**: 이 doc_type은 dev/test에만 있어 holdout 검색 코퍼스의 Lv0 범위는 변하지 않습니다. 새 템플릿의 집계 문서가 들어오면 규칙 5의 "PII 없는 현황"에 해당하는지 확인해야 합니다.
- **Lv2 전체 복원**: 고위험 라벨까지 전부 복원되므로 복원 감사 로그와 출력 재검사가 더 중요해집니다.

## 7. 결정 사항과 남은 항목

결정(2026-11-06)
1. 경조사공지: 직원 가족 정보가 있어도 **Lv0 유지**
2. 민원현황: PII가 없으므로 **Lv0**
3. 한도심사결과: 내부 심사 판단이 있어 **Lv2**
4. 카드발급심사: 같은 이유로 **Lv2**
5. 회의록: **Lv1**
6. Lv2 복원 범위: **전부 복원**(부분 복원은 추후 논의)

남은 항목
1. 부분 복원(`partial`) 도입 여부와 시점. 추가 과제 "권한별 부분 복원"과 함께 다룰 수 있습니다.
2. 문서 단위 예외(예: 인사 내용을 다룬 업무메일)를 `doc_meta`로 2차에 처리할지 여부.
3. 미등록 doc_type이 검색에서 제외될 때 감사 로그에 `unregistered_doc_type` 경고를 남길지 여부.
