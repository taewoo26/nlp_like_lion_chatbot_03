# 토큰 분류 모델 선정 분석 보고서

실전 프로젝트 1 · 2026년 10월 23일 후보 선정 근거

**목적:** 공개 모델 사양·라벨 대응·선정 이유를 보존합니다. 모델 후보를 정한 당시의 근거이며 최신 성능표는 포함하지 않습니다. 최신 구현·평가 결과는 [평가 보고서](탐지%20모델%20코드%20최종%20보고서.md)를 봅니다.

## 1. 선정 목적과 결론

이번 실험에서는 금융 문서에 포함된 개인정보를 토큰 분류 모델로 탐지하고, 기존 규칙 기반 탐지 결과와 비교한다. 기준 모델은 `BCCard/MoAI-Privacy-Filter-INT8`이며, 추가 모델로 `1T/veil-pii-ko-lite`와 `atonlee/koelectra-ko-pii-ner`를 선정했다.

선정할 때 가장 중요하게 본 것은 우리 평가 라벨과의 대응, CPU 실행 가능성, 구현에 필요한 작업량이다. 이름·전화번호·이메일·주소뿐 아니라 주민등록번호·계좌번호·카드번호도 각각 구분할 수 있어야 한다. 번호 세 종류를 한 라벨로 출력하는 모델은 별도 규칙을 덧붙여야 하므로 이번 우선 비교 대상에서 제외했다.

작성 당시에는 후보 선정 단계였으며 dev 정확도와 처리시간을 측정하기 전이었다. 아래 사양은 당시 확인한 공개 모델 카드를 바탕으로 정리했다. Veil을 먼저 구현하기로 한 것은 실행 준비와 과제 적합성을 고려한 판단이며, 성능이 가장 높다고 확정한 의미는 아니다.

## 2. 비교 모델 개요

| 항목 | MoAI INT8 | Veil | KoELECTRA |
| --- | --- | --- | --- |
| 역할 | 기준 모델 | 추가 모델 1 | 추가 모델 2 |
| 저장소 | BCCard/MoAI-Privacy-Filter-INT8 | 1T/veil-pii-ko-lite | atonlee/koelectra-ko-pii-ner |
| 기반 | openai/privacy-filter | KoELECTRA-base-v3 | KoELECTRA-small-v3 |
| 규모 | INT8 ONNX 그래프 파일 합계 약 1.618GB | 약 110M 파라미터 | 약 14M 파라미터 |
| 태깅 | BIOES | BIOES | BIO |
| 공개 라벨 수 | 29종 | 32종 | 29종 |
| CPU 실행 경로 | ONNX Runtime | INT8 ONNX Runtime | Transformers 또는 ONNX |
| 모델 라이선스 | Apache-2.0 | Apache-2.0 | Apache-2.0 |

파일 용량과 파라미터 수는 서로 다른 지표다. 이 표만으로 실제 메모리 사용량이나 속도를 비교하지 않는다. 공개 파일과 기본 정보는 각 모델 카드 [1–3]를 참고했다.

## 3. 기준 모델: MoAI-Privacy-Filter-INT8

MoAI INT8은 한국어와 영어 개인정보 탐지를 위한 ONNX 모델이다. 부모 모델을 INT8로 양자화했으며, CPU 실행을 전제로 제공된다. 학습 데이터는 BC카드의 privacy-filter-openpii-masking 계열로, 공개 PII 데이터와 한국어·영어 합성 시나리오를 포함한다.[1]

우리 평가에 필요한 7종을 별도 라벨로 지원한다. 현재 카드에는 29종, BIOES 클래스 117개로 명시되어 있다. 이전 자료의 라벨 수와 차이가 있으므로 구현에서는 실제 내려받은 버전의 `config.json`을 기준으로 확정한다.

주의할 점은 일반적인 Transformers 토큰 분류 모델과 실행 방법이 다르다는 것이다. 이 저장소에는 PyTorch 가중치가 없으며 ONNX 출력도 완성된 개체가 아닌 logits다. 공식 검증 경로는 BIOES 제약 Viterbi 디코딩과 공백 경계 보정을 거친다. 토큰별 argmax로 대체한 결과를 공식 경로와 동일하다고 볼 수 없다. 1024토큰을 넘는 문서는 분할과 결과 병합이 필요하다.[1]

이 모델은 프로젝트의 기준점으로 사용한다. 추가 모델이 기준 모델보다 가볍게 실행되는지, 정확한 개인정보 경계와 종류를 어느 정도 유지하는지 확인한다.

## 4. 추가 모델 1: Veil

Veil은 KoELECTRA-base 기반의 한국어 개인정보 토큰 분류 모델이다. INT8 ONNX와 실행 코드가 함께 제공되며, 결과를 원문 문자 위치로 반환한다. 공개 실행 코드에는 BIOES 제약 디코딩, 조사 제거, 긴 입력을 위한 창 분할 기능이 포함되어 있다. 우리 평가 코드와 연결할 때 필요한 작업이 비교적 명확하다는 점을 우선 선정 이유로 보았다.[2]

학습에는 BC카드 데이터와 한국어 합성·스트레스 데이터 등이 사용되었다. 기준 모델과 데이터 계열이 일부 겹치므로, 두 모델을 완전히 독립적인 학습 데이터로 만든 비교군이라고 설명하지 않는다.

가장 먼저 확인할 약점은 띄어쓰기 변형이다. 제작자 실험에서는 글자 사이에 공백을 넣은 입력에서 성능이 크게 떨어졌고, 번호의 구분자를 없앴을 때도 성능 하락이 있었다. 우리 데이터의 띄어 쓴 이름과 완전히 같은 실험 조건은 아니지만, `spaced_name`과 전화번호 표기 변형을 별도로 점검할 근거가 된다. 실행 코드의 주소 병합 옵션도 결과에 영향을 주므로 설정값을 기록해야 한다.[2]

Veil은 7종 라벨 대응, BIOES 방식, CPU 실행 코드 제공이라는 조건을 함께 충족한다. 따라서 세 모델 중 먼저 연결해 공통 실행 흐름을 확인할 대상으로 선정했다.

## 5. 추가 모델 2: KoELECTRA

`atonlee/koelectra-ko-pii-ner`는 KoELECTRA-small 기반 모델이다. 약 14M 파라미터로 구성되며, 약 14.7MB의 INT8 ONNX 파일도 제공한다. 금융 PII 데이터와 한국어 PII 데이터, 별도로 작성한 식별자 변형·미끼 사례를 학습에 사용했다고 설명한다.[3]

이 모델을 선정한 이유는 작은 모델에서도 필요한 7종을 직접 구분할 수 있기 때문이다. Veil과 함께 비교하면 경량화에 따른 정확도와 처리시간의 차이를 확인할 수 있다. 다만 크기가 작다는 이유만으로 가장 빠르거나 정확도가 낮다고 미리 결론 내리지는 않는다.

태깅은 BIO 방식이다. 서브워드 단위 출력을 이어 붙여 원문 기준 개체로 복원해야 하며, 이름 라벨이 `PERSON`이 아닌 `NAME`이라는 점에도 주의해야 한다. 주소는 건물번호 등이 포함된 `ADDRESS`와 장소를 나타내는 `PLACE`가 구분된다.[3]

보고서에는 BIO와 BIOES의 차이를 명시한다. 과제에서 모든 추가 모델에 BIOES를 엄격히 요구한다면 이 모델의 비교 허용 여부를 확인해야 한다. 출력 span 형식을 통일하는 것만으로 모델의 학습 태깅 방식이 바뀌지는 않는다.

## 6. 프로젝트 라벨 대응

| 프로젝트 라벨 | MoAI INT8 | Veil | KoELECTRA |
| --- | --- | --- | --- |
| person | PERSON | PERSON | NAME |
| phone_number | PHONE | PHONE | PHONE |
| email | EMAIL | EMAIL | EMAIL |
| address | ADDRESS | ADDRESS | ADDRESS |
| resident_registration_number | RRN | RRN | RRN |
| account_number | ACCOUNT_NUMBER | ACCOUNT_NUMBER | ACCOUNT_NUMBER |
| card_number | CARD_NUMBER | CARD_NUMBER | CARD_NUMBER |

세 모델 모두 위 7종을 별도로 출력할 수 있다.[1–3] 평가에서는 이 대응표를 고정하고, 날짜·기관명·URL 등 범위 밖 라벨은 별도로 취급한다. 현재 프로젝트 공통 인터페이스에는 `organization`도 있지만, 이번 7종 비교에 자동으로 포함하지 않는다.

`FRN`, `VIRTUAL_CARD_NUMBER`, `PLACE`처럼 유사한 라벨을 임의로 합치지 않는다. 추가 매핑이 필요하면 근거와 적용 범위를 먼저 기록한다. 모델이 처음부터 잘못 분류한 결과를 정답 정보를 이용해 고치는 일도 없어야 한다.

## 7. 실험 자료 안내

공개 모델 카드의 F1은 평가 데이터·디코딩 조건이 달라 프로젝트 후보 순위로 직접 사용하지 않습니다. 실제 프로젝트의 비교 조건·지표·측정 결과는 [평가 보고서](탐지%20모델%20코드%20최종%20보고서.md), 개선 전 모델별 상세 표는 [초기 후보 비교표](detector_comparison.md), 실행 방법은 [사용 안내](detector_handoff.md)에서 관리합니다.
