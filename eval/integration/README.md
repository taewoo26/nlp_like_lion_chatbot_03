# 통합 테스트 (eval/integration)

설계 기준은 `통합테스트_설계서_v4.3.xlsx`, 데이터는 `data/integration_v1/` 입니다.
흐름은 **실행 한 번 → 영역별 채점 → 보고서 하나**입니다. 저장소 코드(starter, service, eval/*.py)는 import 해서 쓰기만 하고 고치지 않습니다.

## 바로 쓰기 (저장소 루트에서)

```bash
# 전부: DB를 비우고 기존 문서 + 통합 테스트 84건을 인물사전 OFF·ON 두 번 적재하며 R0~R3, 권한 API, 채점까지
python -m eval.integration.run --rebuild-db --yes

# 기존 문서 파일이 기본값(data/holdout/holdout_labeled.jsonl)과 다르면
python -m eval.integration.run --rebuild-db --yes --holdout data/holdout/다른파일.jsonl

# 영역별로: 검색 평가만(LLM 없음) → 같은 실행 ID에 답변 평가만 → 권한 API만
python -m eval.integration.run --run-id it3 --rebuild-db --yes --only search
python -m eval.integration.run --run-id it3 --resume --rebuild-db --yes --only answer
python -m eval.integration.run --run-id it3 --resume --only security

# 다중 턴 대화만 (ITM01~05, 인물사전 ON 설정 R1·R3 × Lv0·Lv1·Lv2 = 30개 대화, LLM 최대 60번)
python -m eval.integration.run --run-id it3 --resume --rebuild-db --yes --only dialog
#   두 번째 명령: 지금 DB(검색이 끝난 인물사전 ON 적재)로 R1·R3 답변을 먼저 하고, R0·R2 답변 때만 OFF로 다시 적재합니다.
#   --rebuild-db 를 빼면 DB가 맞지 않는 R0·R2 는 '미실행'으로 남고 안내가 나옵니다. 남은 질문이 없는 적재는 다시 적재하지 않습니다.

# 빠른 점검: 질문 10개, 검색만
python -m eval.integration.run --limit 10 --only search

# 중단된 실행 이어서 (정상 실행된 질문은 건너뛰고 실행 오류·미실행만 다시 실행)
python -m eval.integration.run --run-id it3 --resume

# 채점 기준만 바꿔서 다시 채점 (실행 기록 재사용, LLM·DB 호출 없음)
python -m eval.integration.report --run outputs/it/it3

# 채점 로직 테스트 (DB·LLM 없음)
python -m pytest eval/integration/test_scoring.py -q   # pytest 는 requirements-dev.txt
```

## 적재 방식

`--rebuild-db` 는 설정 묶음(인물사전 OFF: R0·R2 / ON: R1·R3)마다 다음 순서로 적재합니다.

```
docker compose down -v → up → 기존 문서(홀드아웃) 적재 → 통합 테스트 84건 추가 적재(--reset 없이) → 질문 실행
```

- 두 파일을 합친 파일은 만들지 않습니다. 저장소 적재 코드가 추가 적재를 지원합니다 (문서 ID가 겹치면 적재 코드가 멈춤).
  인물사전 ON 추가 적재는 기존 인물 후보와 새 후보를 함께 다시 판별하므로, 기존 문서 인물과의 오병합도 실제로 생기고 채점됩니다.
- `down -v` 는 Docker 프로젝트(`--compose-project`, 기본 `IT_COMPOSE_PROJECT` 또는 `pii_starter`)의 DB를 통째로 지웁니다(적재 데이터·감사 로그 삭제). 원본 data/ 파일은 그대로입니다. 실행 전에 프로젝트 이름과 함께 확인을 묻고 `--yes` 면 묻지 않습니다.
- **안전장치:** 지우기 전에 DB 문서를 확인해 기존 문서(홀드아웃)·통합 테스트 문서가 아닌 문서가 있으면 멈춥니다 (개발 DB 보호). DB에 연결할 수 없을 때(컨테이너가 멈춰 있을 때)는 안을 확인할 수 없으므로, 그 Docker 프로젝트에 볼륨이 남아 있으면 멈춥니다 (볼륨이 없는 첫 실행은 그대로 진행). 지워도 되면 `--wipe-other-data`. `--yes` 로는 넘어가지 않습니다. 가능하면 테스트 전용 `--compose-project` 를 쓰세요.
- 적재 순서: 지금 DB와 같은 적재(ON/OFF)부터 실행하고, 남은 질문이 없는 적재는 다시 적재하지 않습니다.
- 검색은 전체 적재 문서 대상, 탐지·인물 판별 채점은 정답 표시가 있는 84건 기준입니다. 유출 검사에는 기존 문서의 개인정보도 넣습니다.
- DB 확인: 통합 테스트 84건, 기존 문서 수 = 홀드아웃 문서 수, 인물사전 ON/OFF. 이어서 실행할 때는 문서 ID 해시·청크 수·연결 수까지 비교합니다.
- 테스트 데이터는 완성된 JSONL 을 그대로 씁니다. 실행 전에 파일 내용 해시를 `it_manifest.json` 기록과 대조하고, 다르면 멈춥니다. 원본(it_source)에서 다시 만들 때만 `--prepare-data` 를 붙입니다.

## LLM 호출 제한 (429)과 이어서 실행

평가 실행 중에만 저장소의 `chat._post_llm` 대신 `common.LLMGuard` 가 LLM을 부릅니다 (저장소 코드는 그대로).

| 환경변수 | 기본 | 뜻 |
|---|---|---|
| `IT_LLM_QPM` | 50 | 분당 요청 수 상한 |
| `IT_LLM_TPM` | 50000 | 분당 토큰 상한 (입력 + 최대 출력 토큰) |
| `IT_LLM_EST_OUTPUT` | 1024 | `LLM_MAX_TOKENS` 를 안 정했을 때 요청마다 잡을 출력 토큰 |
| `IT_LLM_RETRIES` | 6 | 일시적 오류 재시도 횟수 |
| `IT_LLM_MAX_WAIT` | 90 | 재시도 간격(지수 백오프) 최대 초. 서버가 준 대기 시간은 줄이지 않음 |
| `IT_LLM_MAX_HINT` | 600 | 서버가 이보다 길게 기다리라고 하면 사용량 한도 소진으로 보고 멈춤 |

CLOVA Studio HCX-007 한도는 테스트 API 키 60 QPM·60,000 TPM, 서비스 API 키 180 QPM·300,000 TPM 입니다 (`IT_LLM_QPM=170 IT_LLM_TPM=280000`).

- 일시적 제한(429 `42901`·`42902`, 5xx, 타임아웃)만 재시도합니다. 사용량·결제·인증 오류(`insufficient_quota`, `40170`, 401·403)는 바로 멈춥니다.
- 오류마다 HTTP 상태·오류 코드·메시지를 화면에 출력하고 `llm_calls.jsonl` 에 남깁니다.
- 실행 오류가 3번 연속(`--stop-after`)이거나 Ctrl+C 로 멈추면 결과·manifest 를 저장하고 부분 보고서를 만든 뒤 이어서 실행할 명령을 출력합니다.
- `--resume` 은 이전 실행과 데이터·기존 문서·설정·실행 환경(모델·임베딩)·커밋·DB 상태가 같은지 확인하고, 다르면 멈춥니다(`--allow-mismatch`).
- 같은 실행 ID를 `--resume` 없이 다시 쓰면 기존 기록을 지우지 않고 멈춥니다.

## 결과 값과 집계

| 결과 | 뜻 | 통과율 |
|---|---|---|
| 통과 / 실패 | 챗봇 성능 | 통과 ÷ (통과 + 실패) |
| 수동 확인 | 자동으로 단정할 수 없음 (예: 필수 사실이 부정 표현과 함께만 나옴) | 제외 |
| 실행 오류 | 429·타임아웃·DB 연결 등. 챗봇 오답 아님 | 제외 |
| 미실행 | 실행 대상 목록에 있지만 기록 없음 (결과 파일이 없는 설정 포함) | 제외 |
| 채점 미구현 | 실행 경로·기능이 없어 자동 판정하지 않음 | 제외 |
| 기준선 기록·판정 보류·실행 대기·조건 미충족·미검증 | 설계서 04 시트 판정 코드 | 제외 |

- 실행 전에 '설정 × 영역 × 질문' 실행 대상 목록을 `manifest.json` 의 `plan` 에 확정하고, 완료율은 이 목록 기준으로 셉니다.
- 지표는 **전체 기준**이 기본이고 난이도·dev·check 는 보조입니다. R0~R3 비교는 모든 설정에서 정상 실행된 **같은 질문 집합** 기준 지표를 따로 냅니다.
- 필수 보안 판정은 필수 권한 케이스가 모두 판정되고, **설계상 R0~R3 전체 답변의 유출 검사**가 끝나야 '조건부 충족'이 될 수 있습니다. 일부만 돌리면 '검증 미완료'입니다.

- `manifest.json`: 실행 조건 (설정별 환경값, 기존 문서, 실행 환경, DB 상태, 커밋, 데이터 해시, 실행 대상 목록, 세션별 LLM 통계, 상태)

- `traces/search_<설정>.jsonl`, `traces/answer_<설정>.jsonl`: 질문별 단계 기록 (가명처리 질문, 토큰, 실행 당시 키워드, BM25 전후 후보, 검색 순위, LLM 입력 문서, 답변, 상태, 재검사)

- `report/results.csv`: 04 시트 **결과 기록표(tblResult)** 와 같은 15열 (실행 ID·시나리오 ID·케이스 ID·실행 설정·실행 권한·계정·…·검증 키)
- `report/set_results.csv`: 04 시트 **질문 집합 지표(tblSetResult)** 와 같은 10열

## 엑셀에 넣기

1. 두 CSV를 04 시트 해당 표 첫 행부터 그대로 붙여 넣습니다 (열 순서가 같음).
2. 04 시트 A6 '집계할 실행 ID' = 실행 ID, E6 'API 평가 설정' = `--api-config` 값(기본 R2).
3. 01 시트 영역별 현황, 04 시트 설정별 비교·보안 검증 목록이 채워집니다. 검증 키 = `실행 ID|케이스 ID|실행 설정|실행 권한·계정|시나리오 ID`
   (질문은 권한 Lv0~Lv2, API는 사번). 엑셀 보안 판정과 `summary.md` 의 필수 보안 판정은 같은 범위로 셉니다:
   필수 API 18건(케이스·X04·X06, ITP20은 X06 제외) + R0~R3 질문 472건(X04·X06) + 질문 추가 보안 검사 32건(G12~G15).
   대화(실행 단위 '대화')의 X04·X06 실패도 보안 판정을 미충족으로 만들지만 필수 개수에는 넣지 않습니다 (엑셀 v4.4부터 04 시트 E173).
4. 설계서를 고친 뒤 원본을 다시 내보낼 때: `python eval/integration/export_design_csv.py --xlsx 통합테스트_설계서_v4.4.xlsx --out data/integration_v1/it_source`
   (v4.2 이후 표 헤더 기준, 필요한 열이 없으면 멈춤) → `run.py --prepare-data`

## 알아 둘 점

- 답변은 서비스 API(`/api/chat`)를 사용자 레벨 계정마다 따로 호출합니다 (R0~R3 기준 472회 = 질문 × 설정 × 사용자). X04(원문 유출)는 실제 API 응답 전체(답변·문서 조각·가명처리 질문 등 모든 문자열)를, X06(감사 로그)은 요청마다 `audit.query_log` 를 실제 API 응답(상태·반환 문서)과 대조해 채점합니다. 문서 접근 필터(G01·G02·G16)가 생기면 같은 경로로 바로 검증됩니다.
- 권한 API는 `--api-config`(기본 R2) 설정으로 돌고, 결과 행의 실행 설정에 그 값이 들어갑니다. 실행 전에 DB의 인물사전 적재 상태가 그 설정과 같은지 확인합니다. 전체 실행에서는 그 설정의 적재를 마지막에 두어 재적재 없이 이어서 돌고, 다르면 `--rebuild-db` 일 때만 다시 적재합니다 (아니면 권한 API를 건너뛰고 보고서에 이유를 남김). `security` 를 따로 돌릴 때도 다르면 멈춥니다.
- 문맥 판단이 필요한 금지 사실(한 문서의 다른 고객 정보 등)은 비고에 "수동 확인 필요"로 표시됩니다.
